F.1 | plan-continue orchestration that finds the in-progress plan (CLAUDE.md §10) of the current worktree/repo, diagnoses the remaining work and the plan↔actual (git/code) sync state, corrects the plan if they diverge, then continues with the next action when it is clear.
F.2 | It also takes in human review comments from that branch's PR.
F.3 | Use on an explicit `/c` call or a request like "let's continue the work in progress". Not for simple questions, exploration or starting new work (creating a new plan is dlc's job).
H.1 | Find the in-progress §10 plan, diagnose **the remaining work + the sync state**, correct a diverged plan to match the actual state, and then, if the first unchecked Task is clear, continue running it (on an exception, stop and present).
H.2 | The automated version of CLAUDE.md §10 **Start**·**In-progress sync** — **CLAUDE.md wins on conflict**.
A.1 | An explicit `/c` call, or when you are about to continue a plan that was in progress.
A.2 | Not for simple questions, exploration, read-only work or starting new work.
A.3 | **If there is no plan, do not create one** (that is the job of dlc / the start of work).
D.1 | ## Behavior (3 steps: find → diagnose → correct·continue)
1.1 | `ROOT = git rev-parse --show-toplevel`, `BR = git rev-parse --abbrev-ref HEAD`.
1.2 | Search locations (only those that exist, deduplicated): ‖ 1. `<ROOT>/plans/`
1.3 | When the cwd is a worktree, the main worktree's plans — the first `worktree <path>` line of `git worktree list --porcelain` → `<main>/plans/`. Skip it if it is the same as (1).
1.4 | plans/ is independent per worktree (branch), so look at both to miss nothing (it is tracked, but its content differs per branch).
1.5 | **Matching** (§10 rule): the dir whose **dir name** (`<YYYY-MM-DD>-<slug>`) contains the `BR` string → the one `*-plan.md` in it.
1.6 | - 1 → adopt it. ‖ - 2+ → present the candidate list and let the user choose. ‖ - 0 → fallback.
1.7 | read the frontmatter of every plan in the search locations (`*/*-plan.md` + `*.md` directly under each plans/ root), and **present those with `status: in_progress|blocked` sorted by `updated` descending → the user chooses**.
1.8 | Do not pick one automatically by guessing.
1.9 | If all are done or none exist, report "no plan to continue" and stop.
2.1 | Read the plan (together with the plan log in the same folder if there is one — it carries over earlier review dispositions and Deferred items)
2.1b | and look at two axes.
2.2 | If the frontmatter has `intent:`, also read that `intent.md` (§10 bundle intent) — the common Constraints, Open questions and `# Plans` (sibling plans) live there, so the delta in the plan's `# Goal` labeled bullets alone does not restore the requirement.
2.3 | If the file is missing, one line "intent link broken" in the report (a correction target in step 3).
2.4 | Read and correct an old-format plan (no `# Tasks`) by the §10 mapping table.
2.5 | **Remaining work**: `status` + the unchecked items of `# Tasks` (the first item = the next action) + `# Blockers`.
2.6 | `done` → note "already done", then ask whether to continue anyway.
2.7 | `blocked` → show `# Blockers` and judge whether it can be unblocked.
2.8 | No unchecked Task, or the first item is no longer valid → rebuild it from the actual state in step 3.
2.9 | | Freshness | frontmatter `updated` vs the latest commit date | `updated` is long past |
2.10 | | Task paths exist | check that the backtick paths of unchecked Tasks exist | missing/moved files |
2.11 | | Commits reflected | `git log --oneline origin/main..HEAD` | commits not in any checked Task |
2.12 | | Unreflected changes | `git status --short` | uncommitted changes not in any Task |
2.13 | | Completion | is `git log --oneline origin/main..HEAD` empty / `git branch --merged origin/main` | merged but `status≠done` |
2.14 | | Plan integrity | `node scripts/plan-lint.js <adopted plan>` (if present) | violations of the §10 format (mandatory frontmatter keys, mandatory sections, Tasks checkboxes and dates) and **broken Acceptance references** |
2.15 | If a check command fails (no origin, etc.), skip only that check and state it in the report.
2.16 | **plan-lint violations are shown and corrected (not a hard stop)** — reflect them in the step 3 correction.
2.17 | **PR review intake** (only when a plan matched, read-only): collect the **human** review points of that branch's PR (summary, conversation, **inline line**) and pass them to the step 3 disposition.
2.18 | Identify the PR: `gh pr list --head <BR> --state all --limit 3 --json number,state,title`.
2.19 | Collect (3 sources — **inline is mandatory, since it is the main form of code comments**):
2.20 | Review summary·state: `gh pr view <n> --json reviews` (`reviews[].body`·`state`·`author`).
2.21 | Conversation comments: `gh pr view <n> --json comments`.
2.22 | **Inline (line-level) comments**: `gh api repos/{owner}/{repo}/pulls/<n>/comments --jq '.[] | {user:.user.login, path, line, body}'`.
2.23 | ⚠️ `gh pr view --json reviews,comments` **does not return** inline comments (cli/cli #11477) — missing them misreports the code comments the user left as "none" (silent false-negative).
2.24 | **Humans only**: exclude when `user.login` (or `author.login`) equals the current user (`gh api user --jq .login`) (self), and when it ends with `[bot]` (bot).
2.25 | **fail-open**: `gh` not installed, not authenticated, no remote or no PR → skip only this check and one line "PR review: could not check (<reason>)".
2.26 | (2–3 network round trips, only when a plan matched.)
3.1 | If there is a sync divergence, **correct the plan file first** (the main agent is the single writer; §10 in-progress sync)
3.2 | A commit not in any checked Task → check the Task that commit finished (if there is none, add it as a checked Task) + the commit date (do not write the sha).
3.3 | `wip:`·`fixup!` commits are not grounds for checking.
3.4 | Uncommitted changes → reflect the current state.
3.5 | Missing/moved files → update the paths of unchecked Tasks.
3.6 | A `status` that differs from reality → correct it (merged=done, stuck=blocked + `# Blockers`).
3.7 | (merged=done is **recording an objective fact** — once it is done, it stops at exception 5 below, so it is distinct from the done confirmation of e's step 4 and safe.)
3.8 | An unchecked Task that is no longer valid → rewrite it, and put the actual next action at the top of the unchecked items.
3.9 | frontmatter `updated:` to today.
3.10 | A broken `intent:` link → restore it with `git show` from a sibling worktree or the preceding branch per the §10 limits; if that is impossible, remove the link and report.
3.11 | `# Decisions` that differ from reality → the §10 way (rewrite with the reason, move the displaced option to the rejected ones).
3.12 | (a) **Code comments** (bugs, change requests) → add a `- [ ] PR#n address review: <gist>` Task at the top of the unchecked items
3.13 | (judge unresolved ones from the comment state and later commits; if unsure, show them as they are)
3.14 | (b) **Corrections to how you work** (style, procedure) → include the §12 feedback memory saving **judgment** in the report (if it is a target, propose saving; the save itself only after user confirmation — the judgment duty is the same as the dlc Report, but intake was not instructed by the user, so confirm before saving).
3.15 | **Summary report**: plan location·title·status / remaining work (unchecked Tasks·`# Blockers`) / sync diagnosis·corrections / PR review intake result / next action.
3.16 | if the first unchecked Task is clear, proceed right away without re-asking "may I proceed?".
3.17 | An implementation that changes code/files goes to the dlc pipeline regardless of size, and **since dlc applies the wt-first gate whenever it is not in a work worktree (on main or outside), worktree isolation stays in place** (not a bypass — but creating the worktree itself is local and reversible, so create it without asking and report the information to undo it, §1 risk-based approval)
3.18 | **However, on the exceptions below, stop and wait for the user's decision (closed list of 5)**
3.19 | 1. `status: blocked` or `NEEDS-HUMAN:` in an unchecked Task — unblocking is the user's part.
3.20 | 2. A **fallback choice** is needed because plan matching failed (step 1) — get the user's choice even if there is only 1 candidate.
3.21 | 3. The unchecked Tasks were missing or no longer valid and were **rebuilt** — confirm the direction once.
3.22 | 4. The next action is **destructive, irreversible or publicly visible** (push, merge, delete, deploy, DB migration/write, etc. — the §8 gates and their equivalents; if the classification is unclear, stop) — explicit confirmation.
3.23 | 5. A `done` plan — confirm whether to continue.
3.24 | But if that branch's PR is `OPEN` (QUEUED/UNKNOWN of `/e` merge mode), it is not finished but **waiting to merge** — if it is in the merge queue, wait until it finishes, then suggest rerunning `/e merge` (an external write, so confirm per exception 4).
B.1 | **Destructive or publicly visible actions are not continued** (push, merge, delete, deploy — §8 gates) — other clear first unchecked Tasks are continued (the 5 exceptions of step 3).
B.2 | **PR review intake is read-only** — it only collects and classifies comments; **no automatic replies, comments or resolves**.
B.3 | If there is no plan, **do not create one** — only report "no plan to continue".
B.4 | On a matching failure, no automatic choice by guessing — always present the list.
B.5 | Not delegated to a subagent — the main agent is the plan's single writer. The main agent reads and corrects directly.
B.6 | Plan corrections are **facts only** — record only what git or files confirm. Do not check Tasks or fill Decisions by guessing (CLAUDE.md §1).
