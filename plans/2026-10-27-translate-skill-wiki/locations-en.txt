Q.1 | Find the related pages with `uv run --no-project python "${CLAUDE_SKILL_DIR}/wiki_search.py" <query terms…>` and read them.
Q.1a | The shared wiki (`CLAUDE_SHARED_WIKI`, otherwise `~/.claude/wiki`) is found regardless of cwd, and the repo wiki is found by walking up from the current directory to the repo root; both are searched together. If both are the same path, it is found once.
Q.1b | Each result shows the layer (`[공용]` (shared)/`[repo]`), the absolute path, the index summary and the matching body lines.
Q.1c | A matching line carries its section and line range (`L20 §결정 (L18-35): …`). To read only the section, give that range to Read's offset·limit.
Q.1d | Each result carries the related pages linked within the same wiki (`관련: → 나가는 · ← 들어오는`, i.e. related: outgoing · incoming). Aliases `[[a|b]]` count as links too, and links in index.md do not count as incoming.
Q.1e | `--limit N` (default 5)·`--category C` may go anywhere before or after the query terms. For a word starting with `-` (a flag name), drop the leading `-`.
Q.1f | Structural queries (used instead of query terms): ‖ `--links-to <stem>`: prints every line containing a link to that page (once even if a line has several). Use it to find the affected pages before changing a decision.
Q.1g | `--open`: prints every unresolved `[!open]`·`[!conflict]`.
Q.1h | Both print, per page, `L<line> §<section>: …` records under a header line (layer·name·absolute path). They do not follow `--limit`.
Q.1i | `--category` applies only to the pointing pages (the ones holding the callout).
Q.1j | The first line lists the wikis found and their page counts; use it to confirm where it searched. If the default path has no shared wiki, it searches only the repo wiki, with a warning on stderr.
Q.1k | On exit 1 (no results) or results that miss, search again with other words (English identifiers·synonyms) and scan both `index.md` files directly (the shared one is `~/.claude/wiki/index.md`). A single Hangul syllable (`훅`) is not found.
Q.1l | Exit 2 cases: ‖ There is no wiki, word, category or stem to search. ‖ A query mode was used together with query terms or with another mode. ‖ `CLAUDE_SHARED_WIKI` is not a wiki. ‖ A read error.
Q.1m | The reader of stdout closed first, so the output could not be written to the end (if `| head` closes after receiving everything, there is no error and the exit code is the usual one). ‖ An unexpected error (traceback on stderr).
Q.1n | On exit 2, read the reason on stderr, fix the query or settings and search again — skip the lookup only for `찾을 wiki 가 없다` (no wiki to search).
Q.1o | The score is the idf-weighted sum of stem·title match 3, index summary match 2.5 and body BM25 (capped at 2.2). Hangul is split into 2-grams, so it matches even with particles attached.
Q.2 | Answer from the pages (not raw chunks). Cite the evidence pages **together with which wiki they belong to**.
Q.3 | If it has reuse value, file it in **the current repo's wiki** as `pages/query/<slug>.md` (frontmatter+links) + append to that wiki's `log.md`.
Q.3b | If an answer based on shared pages is worth filing from another repo, route it to the shared-wiki proposal of ingest step 2. Shared pages do not point to pages of private repos.
Q.4 | If there are no related pages, state "not in the wiki" (no guessing). Propose ingest if needed.

L.9 | `check_links.py` — dead links·orphans·outbound<2·index sync: `uv run --no-project python "${CLAUDE_SKILL_DIR}/check_links.py" [wiki path]` (without an argument, the current repo's wiki).
L.9b | Aliases `[[a|b]]` count as links to `a`. But index registration accepts only `[[a]]` without an alias (the same standard as smoke).
L.9c | exit 0 clean, 1 violations — a page or index that is not UTF-8 gets a `UTF-8 아님` (not UTF-8) violation and the rest is still judged (for pages, the same verdict as schema), 2 no pages directory or a read failure (permissions·subdirectories — no violation list, `check_links: 읽기 실패 — <path>: <reason>`, a read failure).
L.10 | `wiki_check.py schema` — frontmatter format: `uv run --no-project python "${CLAUDE_SKILL_DIR}/wiki_check.py" schema [wiki path] [--config file]`.
L.10a | Without a wiki path, it walks up from the current directory to the repo root looking for `wiki/`. For a wiki elsewhere, such as `docs/wiki`, pass the path.
L.10b | exit 0 pass, 1 violations (one `<path>: <rule> — <detail>` line each; the path is relative to the repo root, or to the wiki's parent outside a repo), 2 usage·config·environment error.
L.10c | In a value, as in YAML, everything from a `#` after whitespace is a comment. `[PR #82, …]` is a violation even if closed on that line, since only `[PR` remains.
L.10d | If the `#` is part of an item, quote that item (`["PR #82", …]`); if it is a note, move it to a comment after the `]` (`[a.kt]  # note`). The same goes for a note attached after `[ … ]`.
L.10e | If the note is quoted too, covers becomes a pattern that matches nothing and stale silently misses it.
L.10f | Adapt the rules to that wiki's WIKI.md conventions with `<wiki>/wiki-check.toml`. The template is `templates/wiki-check.toml`, and the key descriptions are in the template's comments.
L.10g | Without a config, it runs on the shared WIKI.md conventions (5 required keys, 5 categories, `created`·`updated` dates). WIKI.md is canonical for the format, so if the two disagree, fix the config.
L.10h | Reading a config needs Python 3.11+ (`tomllib`). On 3.9·3.10 only the checks without a config run.
L.11 | `wiki_check.py stale --report` — covers freshness: `uv run --no-project python "${CLAUDE_SKILL_DIR}/wiki_check.py" stale --report [wiki path]`.
L.11b | It does not use config values for its judgment, but if a config exists, it reads and validates it (config errors below).
L.11c | If there are no pages with `covers`·`verified_at` and no unreadable pages (not UTF-8·frontmatter not closed·a covers value or item that starts with `[` but does not end with `]`), it prints "검사 대상 아님" (nothing to check) and exits 0, so it is safe to run on every wiki.
L.11d | An unreadable page is a "covers 읽기 실패" (covers read failure) violation (exit 1) even without covers. If there are covers pages, run it inside a git repo. The judgment and exit codes are in the Freshness section.
L.12 | `wiki_check.py smoke` — representative questions: `uv run --no-project python "${CLAUDE_SKILL_DIR}/wiki_check.py" smoke [wiki path] [--config file]`.
L.12b | Without `[smoke]` in the config, it prints "검사 대상 아님" and exits 0, so it is safe to run on every wiki. With `[smoke]` but no check filled in, exit 2. Examples are in the template's comments.
L.12c | For each `[[smoke.questions]]`, it passes when `page` (a `.md` path relative to pages) exists, `index.md` has `[[stem]]`, and some line of the body (after the frontmatter) matches `expect`.
L.12d | `expect` is a Python `re` searched line by line like grep. POSIX character classes (`[[:space:]]`) and GNU grep dialects (`\<`·`\>`, `[=…=]`·`[.….]` inside a character set) are read differently by Python `re`, so they are blocked with exit 2 — use `\s`·`[0-9]`·`\b`. The same goes for `[smoke.forbid] patterns`.
L.12e | `[smoke.forbid]` looks at the full text of the pages' `.md` files (frontmatter included) line by line and reports matching lines as FAIL.
L.12f | `branch_names` (whole lowercase names that contain a hyphen and no `/`, after removing the remote name from local and remote-tracking branch names — names containing `/` such as `feat/x-y` are not checked. The remote name is read as one level, so branches of a remote whose name contains `/`, such as `team/fork`, are not checked. It must run inside a git repo; outside a repo, no other check runs either and the whole smoke exits 2),
L.12g | `plan_status` (`status: in_progress`), `patterns` (a list of regular expressions); all are off by default. A sentence that copied in-progress state becomes a wrong fact once that work ends.
L.12h | exit 0 pass, 1 failure (one `PASS | …`·`FAIL | …` line each plus a total), 2 usage·config·environment error.
L.13 | `wiki_check.py schema` is canonical for the frontmatter judgment. The frontmatter line of `check_links.py` is for compatibility, so it treats pages with a BOM and pages without a closing `---` differently.
L.13b | Running `check_links.py` alone does not catch duplicate pages with the same stem (one silently overwrites the other).
L.14 | If a config (`<wiki>/wiki-check.toml`) exists, schema·stale·smoke all read and validate the whole file.
L.14b | Unknown keys·wrong types·`[smoke]` regex errors (POSIX character classes included) make every command exit 2 in whatever section they are,
L.14c | and the hook reads the config only when there are covers pages and reports the error as a `systemMessage` every turn instead of the stale judgment.
L.14d | A single smoke typo also blocks the schema check of ingest step 10, so after fixing the config, run `schema` first.

V.1 | This section is canonical for the meaning, recommendations and judgment of the two keys.
V.1b | If a page that makes claims about code lists that code's paths in `covers`, `wiki_check.py stale` finds the cases where the code changed but the page stayed the same.
V.1c | Both keys are optional, and stale does not look at pages without them.
V.2 | **`covers`** — a list of path patterns (inline `[a, b]` or block `- a`). An inline list must close on one line
V.2b | — if a value or block item starts with `[` but does not end with `]` (a multi-line list, cut off by a comment, characters after `[ … ]`), it is a schema violation and stale treats it as "covers 읽기 실패".
V.3 | Patterns are fnmatch on paths relative to the git top level. They are case-sensitive and `*` crosses `/` (`src/*` also matches `src/a/b.py` — it is not gitignore-style `**`).
V.3b | A pattern identical to the path always matches even if it contains `[`·`?`·`*`.
V.3c | The whole pattern is matched once reading `[…]` as a character set and once reading every `[` literally (`app/[id]/*` matches `app/[id]/page.tsx`).
V.3d | To mix a literal `[` and a character set in one pattern, write the literal one as `[[]` (`app/[[]id]/[ab].py`).
V.3e | An item that is empty, starts with `/`·`./`·`../`, ends with `/` or contains `\` is reported by schema as a violation.
V.4 | What to list (a recommendation — the script does not enforce it): only paths directly tied to claims whose truth changes when the code changes.
V.4b | The evidence is a measurement in one repo — broad covers hit about a third of the commits, and the confirmation became a formality.
V.5 | For the form, exact file paths, `dir/*` and `dir/*.ext` are recommended. These are forms that can be carried over to the `paths:` of `.claude/rules` (glob — `*` matches only within one directory and `**` crosses directories).
V.5b | Patterns whose `?`·`[...]` match `/` and patterns with several `*` cannot be moved as they are.
V.6 | **`verified_at`** — the fingerprint of the covers files' contents at the time the page was checked against the code. `fp1-` followed by 16 lowercase hex characters.
V.6b | The fingerprint is a hash of, for each file in covers (wiki pages excluded), "the (mode, blob) that `git add -A` would record in the index now".
V.6c | It does not look at history, so regardless of fixup·rebase·squash·revert·shallow clones it is decided by one thing: "are the contents now the same as the checked contents".
V.6d | It changes even when only the executable bit changes, or when changing the covers list changes the file set.
V.7 | There is no separate command that makes the value. `stale --report` shows the current value per page.
V.7b | Write that value only after checking the page's claims against the covered files and fixing them, and name the checked files in the commit message that changes the value.
V.7c | Carrying one line of value over clears both the hook and the report, so no tool can stop it from being carried over without a check — this order is the only safeguard.
V.8 | Judgment: if the value equals the current fingerprint, OK; if it differs, STALE (a violation). Without a value, "미확인" (unconfirmed, not a violation).
V.8b | 7–64 hex characters are the old format (a commit value) and a violation — check the page again and replace it with the value the report shows.
V.8c | A version unknown to the script, such as `fp2-`, needs a script update (exit 2).
V.8d | `verified_at` without covers, or covers matching 0 files, is a violation.
V.9 | **Modes** — `uv run --no-project python "${CLAUDE_SKILL_DIR}/wiki_check.py" stale <mode> [wiki path] [--config file]`
V.9a | | Mode | Judgment | Use | ‖ | `--report` | compares `verified_at` with the working-tree fingerprint per page. Does not look at history | audit·lint·CI |
V.9b | | `--branch [--base REF]` | covers files changed in the commits of `merge-base(HEAD, base)..HEAD` but the page did not | CI·before push |
V.9c | | `--stop-hook` | the same judgment as `--branch`, widened to the working tree (untracked included) | Claude Code Stop hook |
V.10 | `--branch`·`--stop-hook` do not look at order — once the page was changed on the branch, later covers changes are not reported either.
V.10b | Changes after the check are caught by `--report`, but only for pages with `verified_at`.
V.11 | The base is decided in this order: `--base`, config `[stale] base`, the default branch candidates (the fork point of HEAD with those of `origin/HEAD`·`origin/main`·`origin/master`·`main`·`master` that are not the current branch).
V.11b | CI passes it like `--base origin/$GITHUB_BASE_REF`. `--report` does not take `--base` (exit 2).
V.12 | `--branch`·`--report` read pages and config from the working tree. If there are uncommitted changes, they write "작업 트리 기준 — … 미커밋 변경 N개" (working-tree based — N uncommitted changes) at the top of the output and on stderr. CI judges by the committed contents.
V.13 | exit: 0 pass, 1 violations (one `<path>: …` line each), 2 usage·config·environment error (outside a repo, git failure, the base could not be decided, a fingerprint version unknown to the script).
V.13b | A page that is not UTF-8, whose frontmatter is not closed, or whose covers value or item starts with `[` but does not end with `]` has unknown covers and is a "covers 읽기 실패" violation.
V.13c | If there are no covers pages (for `--report`, `verified_at` pages too) and no unreadable pages, it prints "검사 대상 아님" and exits 0.
V.14 | **CI conditions and limits of `--report`** ‖ For a value written in an uncommitted state to equal the CI value, commit the checked working tree as it is — no partial staging, no pre-commit formatter changing files, and commit or ignore the untracked files listed in covers.
V.14b | If CI has untracked artifacts listed in covers, STALE appears only in CI and does not clear on re-checking — ignore the artifacts or run on a clean checkout.
V.14c | Cases where the fingerprint differs between machines: before the renormalize commit after changing the line-ending rules in `.gitattributes`, two tracked paths differing only in case (case-insensitive file systems — the macOS·Windows default — vs Linux), ignore rules that differ per machine (`core.excludesFile`·`.git/info/exclude` — the untracked set changes).
V.14d | The fingerprint is computed through git's add path, so clean filters such as LFS run for each changed covers file — slow on large files, and it does not stop what the filter itself writes.
V.14e | `core.fsmonitor` also runs as in a normal `git status`. If set up as a hook, it is also called on git calls against the copy (update-index·ls-files). If `true` (the built-in daemon), status starts the daemon and creates `$GIT_DIR/fsmonitor--daemon*`.
V.14f | Apart from that, the only thing the tool writes is an index copy in a temporary directory — the copy is not written as a split index and does not call hooks in `core.hooksPath` (`post-index-change` etc.), and the real index·shared index·objects stay as they are.
V.14g | submodule gitlink changes: `git add` does not follow `diff.ignoreSubmodules`, so neither does the fingerprint. HEAD moves of a submodule with `submodule.<name>.ignore = all` are not in the fingerprint.
V.14h | The fingerprint follows the effective value where `.git/config` overrides `.gitmodules`. `git add -A` of git 2.54.0 follows only the `.gitmodules` value. So if this value is only in `.gitmodules`, the two agree.
V.14i | If `.git/config` changes whether it is `all` (putting `all` only in `.git/config`, or overriding `all` in `.gitmodules` with `none`), the fingerprint differs after the commit either way. `git add` before 2.54 does not follow this setting (2.54.0 release notes), so the `.gitmodules` side disagrees too.
V.15 | **Clearing the notice** — the hook keeps no state, so it notifies again at the end of every turn until cleared.
V.15a | Check the page's claims against the covered files and fix them. If there is `verified_at`, carry the value over after the check too.
V.15b | If the change is unrelated to the claims, narrow covers. If there is `verified_at`, the file set changes and so does the fingerprint, so write the value again.
V.15c | To turn the hook off in this repo, put `[stale] stop_hook = false` in `<wiki>/wiki-check.toml` (when a global registration overlaps a repo with its own gate). It does not affect `--branch`·`--report`.
V.16 | **Registering the hook** — this skill does not register hooks or CI. Rules to follow when registering:
V.16a | The script path must exist on every machine that uses those settings. If it does not, python exits 2, and a Stop hook's exit 2 blocks every stop.
V.16b | Abbreviating the flag (`--st`·`--stop-h`) or attaching a value (`--stop-hook=…`) does not exit 2 (so stopping is not blocked), but it judges nothing and only emits an "인자 오류" (argument error) `systemMessage` every turn. Write `--stop-hook` as is in the registration command.
V.16c | The starting point is the `cwd` of the hook input JSON (once a worktree is entered, that worktree), and relative wiki paths·`--config` are relative to that repo root.
V.16d | Do not use `${CLAUDE_PROJECT_DIR}` in the wiki path — it stays at the session's start location, so a judgment inside a worktree looks at the main checkout's wiki.
V.16e | For locations that are not discovered, such as `docs/wiki`, pass the path.
V.16f | But do not pass the wiki path·`--config` when registering globally (`~/.claude/settings.json`); pass them only when registering in that repo's project settings.
