N.0b | A design review must look at call sites, layers and creation paths together. Collect the following yourself:
N.1 | 1. **Changed file list**: `git diff --stat` (if the caller stated the change scope, use that instead).
N.2 | 2. **Call sites of changed symbols**: trace new/modified public functions, classes and interfaces with `rg` (or `grep -R` if absent). Check whether each call site is in the same layer or a different one.

N.5 | 5. **Related test fixtures**: whether tests inject dependencies with mocks/stubs or instantiate them directly. If tests are hard to write, that is a coupling signal.

V.1 | 1. **Dependency direction** — is it one-way, upper→lower? Reverse dependencies (domain→infrastructure), circular imports, the stable dependencies principle (depending on frequently changing modules).
V.2 | 2. **Layer boundaries** — UI/application/domain/infrastructure boundary violations (UI calling the DB ORM directly, etc.), missing data conversion across a boundary.
V.3 | 3. **Object lifecycle** — whether singleton/per-request/transient fits, races on shared state, repeated creation of expensive objects.
V.4 | 4. **DI/IoC** — constructor/parameter injection vs hardcoded instantiation inside functions, replaceability in tests, overuse of global/module singletons.
V.5 | 5. **Interface location** — Dependency Inversion: whether the interface sits with its users (high-level) and the implementation at the low level, paying the cost of abstraction for a single implementation (premature — the simplify boundary; this agent only covers "insufficient structural justification").
V.6 | 6. **Testable structure** — can it be unit-tested without external infrastructure (DB/network/time/files), excess mocking (= a coupling signal).
V.7 | 7. **Method extraction / separation of responsibilities** — several abstraction levels or several responsibilities (validation+logic+I/O) in one function, 50+ lines with many branches. Whether an extraction would be a nameable unit of meaning.
V.8 | 8. **Extensibility / cost of change** — on a new requirement, modifying existing code vs adding new code (OCP), whether branches force simultaneous edits in N places when an enum/type value is added.
