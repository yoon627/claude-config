---
name: dlc
description: A development-cycle orchestration applied when starting a non-trivial code change (bug fix, feature addition, refactoring). It judges the size — trivial (a typo, one log line) passes the procedure at once (the worktree is used regardless of size), and structural (multi-layer, public API, DB, new service) runs the full pipeline explore→plan→review→TDD→implementation→review→simplify→verification. Applied on an explicit `/dlc` call or automatically for a non-trivial code change. Not for simple questions, exploration or read-only work.

# dlc — automatic development cycle

The main agent is the hub; only reviews and checks run as isolated subagents. The plan file (work records in `<slug>-log.md` in the same folder) is the only shared channel (only the main agent writes it) — its path is `<ROOT>/plans/<YYYY-MM-DD>-<slug>/<slug>-plan.md` (CLAUDE.md §10 convention). This makes the CLAUDE.md §3 workflow concrete — on conflict, CLAUDE.md wins.

## When to use
- An explicit `/dlc` call or a non-trivial code change. For trivial, the size gate passes the *procedure* at once, but **the worktree is used all the same**.
- Not for simple questions, exploration, read-only work or one-turn commands.

## Entry matrix (dlc vs wt vs direct)
Judge the request type to choose the path. The single criterion is **"does it change code/files"** — size only decides *which steps run*, not whether a worktree is used.

| Input type | Path |
|---|---|
| Questions·exploration·read-only (including one-turn commands **that change no files**) | no dlc — work directly where you are |
| trivial change (a typo, one log line) | **dlc trivial in a worktree, via wt** (only the procedure passes at once) |
| non-trivial change (small or larger) | **full dlc in a worktree, via wt** (below) |

## dlc → wt (mandatory at every size)
When code/files change and **the session is not in a working worktree** (on main or outside), dlc creates a worktree with `wt` **before any other action (Explore and implementation included), without exception**, and proceeds inside it. No direct work on main and no detours — a **mandatory gate**.
- **Judgment**: in Setup (step 0), check the worktree location *first of all* (before reading or editing code). Compare the cwd with the first worktree (= main) of `git worktree list --porcelain`; if it is main, wt.
- **Creation without confirmation**: creating a worktree/branch is local and reversible, so it is not subject to approval (risk-based approval — CLAUDE.md §1). The single source of the procedure and the report format is `skills/wt/SKILL.md` request §3~§4 — dlc does not restate it.
- **Loop prevention**: when wt invoked dlc, the session is already inside the worktree, so skip (wt→dlc is normal; the dlc→wt backstop is told apart by location).
- If already inside a worktree, only run the self-check and proceed (CLAUDE.md §3-1).

## 0. Size gate
| Size | Trigger | Steps run |
|---|---|---|
| **trivial** | typo·comment·formatting·import·one log line | implementation → verification → commit → Report (review/plan/TDD skipped — CLAUDE.md §7 exception) |
| **small** | single function/file, <50 lines, single module | Explore → (for a bug, reproduction TDD Red) → implementation → Green → code-reviewer → simplify check → verification → commit → Report |
| **medium** | multiple functions/1 module, 50~150 lines | small + draft plan → plan-reviewer → simplify check (+re-verification) |
| **structural** | multi-layer·public API·DB·migration·new service·150+ lines | full pipeline (below) |

- Size is a **provisional value** — **re-judge** it after Explore and after the implementation diff. If work that started as small grows into public API·DB·2 layers·150+ lines, promote it and bring back the skipped plan-review/arch.
- **Final verification delegation**: the table's 'verification' (every size·structural step 15·where a promotion joins) is **run by the isolated runner and judged by the main agent** (Isolation boundary below). **trivial verification·step 10 Green·step 14 targeted re-verification are done by the main agent directly**. Isolated = the final verification before completion; main agent = minimal·targeted during implementation. Run the final verification **only once, after the changes are settled** (if user requests may keep changing things, wait until they are settled — starting before that means running it again). If the repo provides a command that picks axes from the changed files, use it (`bash scripts/verify.sh changed` for `~/.claude`) — verification of every axis is left to CI and the user's periodic runs.

## Requirement clarification (right after the size gate, non-trivial)
After the size judgment and before Explore, check the requirement for **gaps** — the judgment procedure of §3 "if ambiguous, ask first". Do not fill them with arbitrary inference.
- **Checklist** — 1) the problem and why now (Problem) 2) constraints·boundary conditions (Constraints) 3) completion criteria 4) target files/feature scope 5) the form of user-visible outputs·wording 6) explicit prohibitions/exclusions. If a blank has **even the slightest chance of affecting the completion judgment (acceptance), ask** (`AskUserQuestion`); if unsure, ask (fail-safe). **Only when it is clearly irrelevant to the outcome**, assume, state it in one line and proceed.
- **Record the result in the labeled bullets of the plan's `# Goal`** (right then if a plan exists, otherwise at the step 3 draft plan) — if it ends only in conversation it evaporates, the next session asks the same thing again and **an already rejected option comes back**. CLAUDE.md §10 is the single source of the section definitions (for an old-format plan, the §10 mapping table) — this covers only the conditions and procedure for filling them.
- **For medium or larger, always record them, whether or not there are gaps** (introduced 2026-09-09) — options come back not because a gap went unseen but because the constraint was written nowhere, so a rule that records only when a gap is found cannot prevent it. For small, only when there is a plan and a gap was found; trivial is not subject to `# Goal` labeled-bullet records. Not retroactive for plans made before this rule (2026-09-09), whether you are starting or taking them over.
- **What to write** — `Why:` with content. Constraints·Out of scope with content or `없음 — <one-phrase reason>` (a bare `없음` is forbidden — so that "considered, there is none" is told apart from "forgot", and a reviewer can rebut it. Why this differs from the self-flag's "0 lines if nothing applies": labeled bullets are fixed items, so `없음` records a state rather than inventing one). Open questions only when there are questions you could not narrow down (the next session takes them over). Separate what the user confirmed from what the model inferred — mark inferences with ⚠️ or put them in Open questions (once an inference is fixed as settled, the next session rejects options on a wrong basis).
- **Bundle intent (§10 `intent.md`)** — before the checklist, scan the `plans/*/intent.md` of **every worktree** in `git worktree list --porcelain` for `status: open` (the bundle of an unmerged preceding branch exists only in that worktree — missing it here creates a duplicate of the same bundle). If this requirement is a follow-up of that bundle, link to it instead of creating a new one, and if the file is not in this worktree, bring it in per the §10 limits. If there is none and §10 creation trigger 1 or 3 applies, create intent.md first (trigger 2 goes to the split judgment below for medium or larger, and follows §10 for small). If the linked requirement is a `(not started)` line in that bundle's `# Plans`, replace that line with this plan's real path — a unit that belongs to a bundle gets a plan file regardless of size (trivial included) (there must be a path to put in). The `# Goal` labeled bullets of a linked plan are one link line + the delta only (§10 is the single source of triggers·format·lifetime·ownership — not restated here).
- **Split judgment (medium or larger, introduced 2026-09-16)** — after the checklist, actively check whether this requirement splits into several plans **each of which, merged alone into default in order, leaves the build and conventions valid without contradiction** (the procedure of §10 trigger 2). The criterion is not size but merge consistency (each plan carries the fixed cost of a worktree, a review and a merge) — a case like doc conventions, where "the build does not break, but merging only part makes the conventions contradict each other", does not split. Sequential dependency does not prevent a split (dependencies go in the `# Plans` notes). **If it splits**, create intent.md (if it is a follow-up of an already open bundle, add lines to its `# Plans`) and write one line per unit (only the first plan starts; the rest as `<slug candidate> (not started)`), then pass that draft once, with the other candidate split lines and the reasons for rejecting them, to plan-reviewer in **bundle mode** (`agents/plan-reviewer.md` item 15, codex off; this review covers only new boundaries, not the retroactive trigger 3. Results and dispositions go into the `# Review Disposition` of the first plan's log (step 3) with the prefix `[bundle]`. Review again if the boundaries, dependencies or common constraints change). One line `Split: bundle → <intent.md path>` in the first plan's `# Goal`. The split units each have their own plan (the bundle bullet above), and each unit's size is judged independently by its own gate — a split does not exempt size judgment, and a unit with structural triggers (multi-layer·public API·DB·new service) runs its plan as structural. **If it does not split**, one line `Split: none — <what it tried to split and which coupling prevented it>` in the plan's `# Goal` (a bare `none` is forbidden. If there is only one candidate unit, say so — what is valid only in one merge. Under the exception below, its format). **Exception — follow-ups from the same source may stay bundled in one plan**: units from the same source (one plan's `# Deferred`·Out of scope, or the same open intent) may stay in one plan to save the fixed cost each plan carries, even if they could split for lack of coupling, when each unit can be reverted on its own as a purpose commit of the "Commit units" section below (a judgment that the gain of splitting is worth less than a plan's fixed cost — the same criterion as the bundle mode review). Do not use this exception if units mix within the same file and merge into one commit unit, or if any unit has a structural trigger. In that case the `Split:` line is `none — purpose-commit bundle: <shared source> · <units> · <reason for keeping one plan>`. This judgment is a **provisional value** — settle it after Explore and update it if it flips: none→split, then create intent.md·the bundle review at that point and fix the `Split:` line; split→merged into one, then the remaining plan keeps `intent:` and the `(not started)` lines are deleted (nothing has started, so there is no plan to drop — bundle lifetime per §10). If the premise of a chosen exception (no mixing within the same file·no structural unit) breaks, redo the split judgment. Applies to plans newly made on or after 2026-09-16.
- **silent** — if there are no gaps, proceed **without questions** (zero friction for a clear requirement). This applies only to the question axis — `# Goal` labeled-bullet records follow the rules above.
- **Question design·priority in depth** — the boundary between asking and recommending (ask if something is missing, recommend if only the method differs) · questions whose answer changes the design·acceptance first (if it looks burdensome, one at a time, interview-style) · in an unfamiliar area, a **blind-spot briefing** on pitfalls·criteria·past decisions, then rework the questions · for taste/visual outputs, **prototype-first** (2~4 mockups first). Details in `~/.claude/wiki/docs/dlc-details.md` §A. (For render requests, `dlc-task-router` injects the prototype axis early, at turn start.)
- **trivial is no exception either** — it skips the procedure; it does not allow an unclear requirement. If outputs·wording are ambiguous, ask first.
- Clarification takes ≤2 rounds (the same shape as the fix loop). If re-judging size after Explore widens the scope, re-evaluate the gate.

## ⚠️ self-flag — the side that plans and implements reports its concerns and arbitrary decisions (step 3·during implementation, conditional)

This repo's concern mechanisms are all **on the reviewer side** (plan-reviewer's strong/weak concerns, code-reviewer, architecture-reviewer). Reviewers are isolated spokes, so **they have no way of knowing where the main agent had low confidence**, and if a review does not happen to catch that spot, it passes as is. The spots where the main agent filled in behavior the plan did not decide during implementation are also recorded nowhere — exactly the spots where a person needs to read the code. So the main agent that plans and implements reports them itself.

- **Four closed triggers** — write only in these cases; otherwise **stay silent** (the same shape as the question axis of the requirement-clarification silent rule. Do not write "no concerns"):
  1. Two constraints could not both be satisfied, so one side was chosen
  2. Conventions conflicted and their priority was judged (between equals with no stated precedence)
  3. The design was decided relying on ⚠️inferred (evidence that is only circumstantial)
  4. (during implementation — steps 8~15, small or larger with a plan file) **observable behavior** that the plan·`# Goal`·`# Acceptance` did not decide was decided (including what a test assert decides) — behavior on failure·exception, defaults·thresholds·timeouts, handling of boundary input (empty values·duplicates·concurrent requests), the order·conditions of external side effects (writes·sends·deletes). Write it **only when there were two or more plausible options and the chosen one changes an observable result**. Stay silent on what existing code·call-site contracts·same-layer conventions already decided, on what had only one option, and on internal details whose behavior does not change (names·data structures).
- **Other reports during implementation get the same marker** — in small or larger with a plan file, if during steps 8~15 something matches triggers 1~3, or a §10 sync rewrites a decision in `# Decisions` (a decision *different* from the plan), that line too starts with `⚠️ (구현)` and takes the same disposition·Report path as trigger 4. The marker leaves the self-diagnosis judgment below unchanged ("changed to ~" is a design change) — in particular, a choice that changes an Acceptance pass criterion or a user-visible output must be asked (AskUserQuestion), separately from recording it.
- **Record it in `# Decisions`** — do not create a new section. One line: `⚠️ <concern> — <what it conflicts with> — <chosen side and reason>`. Lines from implementation share only the prefix `⚠️ (구현)`, and the body follows each format — trigger 4 is `⚠️ (구현) <behavior decided> — <other options> — <chosen side and reason> — <file·symbol>` (a symbol instead of a line number — lines shift with later edits). This carries the wiki's `> [!conflict]` practice (WIKI.md) over to the plan.
- **No limit on count or format** — fixing a number of items turns it into the "empty checklist ritual" that [[self-diagnosis-and-improvement-status]] rejected. If nothing applies, 0 lines is the right answer.
- **Disposition takes the same path as review findings** — for triggers 1~3, when calling plan-reviewer at step 6, pass the `⚠️` lines explicitly as "review first", and at step 7 dispose of them **first, together with** the review findings, recording it in the plan log's `# Review Disposition`. Disposition values are kept apart from review findings and are only `resolved` / `accepted-risk` (risk accepted, reason required) / `deferred` — `false-positive` has no meaning for a self-report.
- **Disposition of `⚠️ (구현)`** — these arise after step 6, so pass them into the step 11 code-reviewer input as "review first" (not to arch·Codex — Codex gets independent input), and pass the lines that arise after that along to the step 12 fix loop·step 14 re-review. Disposition values are as above — a choice the reviewer found valid is `accepted-risk` (the chosen side stays — it remains a spot for a person to check); if the reviewer's finding made you switch to the other side, `resolved`. Lines that did not go through a re-review (step 15 verification repairs, re-review skipped) are written as `⚠️ (구현) [리뷰 미경유]`, disposed of by the main agent, and must go into the 16 Report "Where to read". If a reviewer finds an unreported decision and the main agent accepts it, add a `⚠️ (구현)` line; if the reviewer rebuts it and it becomes a finding, write the ⚠️ disposition and the finding disposition together on one line.

## Acceptance — itemization + evidence gate (non-trivial)
Break the requirement down into **testable acceptance items**, and "done" only **when each item is satisfied by evidence (run·observation·pass)**. No "done" without evidence.
- **Itemization** (at the draft plan): in the plan's `# Acceptance`, `what is satisfied` + `how it is checked` (command/observation) + `pass criterion`. Make it observable (no abstract "works well").
- **Test identifiers**: when writing a test (before the evidence gate at the latest), fill its identifier (`path::test_name`; for an observation, the command) into the verification field of the items that test is evidence for. Filling an empty field or appending an identifier to a written command makes the means of verification concrete, so it is not subject to the approval of no-progress below — changing or removing an identifier·command already written while repairing a verification failure (while the no-progress counter runs) is subject to approval. It becomes a source of the 16 Report "Where to read".
- **Evidence gate** (before the Report): check every item against evidence. If anything is unmet or unverified, no completion → fix it, or `status: blocked`/"unverified" (CLAUDE.md §1).
- **verification grounding**: for running artifacts (HTML·SVG·games·charts·CLI·servers), put in evidence from **actually running them and observing the output**, not from static inspection ("well-formed ≠ correct").
- trivial is exempt from itemization (the verification itself is the acceptance) — but it is still verified.
- **Doc sync is acceptance too** (CLAUDE.md §3): if you touch a README-documented component·`wiki/pages/`, update the README/`wiki/index.md` sync on the same branch as an acceptance item (if you forget, it is not done — the shared wiki is not committed on the branch but to its own repo, together, from a main session, §11).
- **Triple backstop**: the Stop hook (`dlc-early-stop`) gives capped warnings (fail-open) — 1) no verification record for a non-trivial change 2) a documented surface changed without a README/index sync (`dlc-doc-drift`) 3) source changed but the plan matching this branch was not touched (`plan-match` — fires only when a plan actually exists; silent otherwise). The hook is a backstop — this convention is the single source.

## Verdict + notification (non-trivial)
**When ending the work**, state the evidence gate result explicitly as one of three values — do not end with "mostly done". If it can still be fixed and you are fixing it, it is not yet a verdict target (keep going).
- **DONE** — every `# Acceptance` item is satisfied by evidence. **Do not set the plan `status` to done here** — per §10, done is the time of merge·deploy·approval (acceptance passing ≠ integration complete. Writing done early makes `/c` treat work waiting for integration as finished and skip it). **The formal completion commit (the last commit of step 16) comes only from this verdict** — purpose commits are made midway per the "Commit units" section below.
- **BLOCKED** — what is needed next is **provision of a resource or fact** (permissions·credentials·an undeployed API·someone else's work). `status: blocked` + *what is needed to unblock it* in `# Blockers`.
- **NEEDS-HUMAN** — what is needed next is **a choice or approval** (choosing an alternative·accepting a risk·reopening a rejected option). Keep `status: in_progress` + `- [ ] NEEDS-HUMAN: <question> — <options>` at the top of the unchecked `# Tasks`. Why it is not folded into `blocked`: a blocked transition is counted as `plan-blocked` **failure** telemetry (`dlc-signal.js`), so a normal wait for a decision would remain as a workflow failure. The status itself becomes the key that tells the two apart.
- If it looks like both (no credentials, and whether to go with a mock must also be decided), decide by **the next single step** — if you must receive something, BLOCKED; if you must choose, NEEDS-HUMAN.
- **BLOCKED·NEEDS-HUMAN make no formal completion commit** (CLAUDE.md §8 — no commit on verification failure). Unit commits already made each passed targeted verification, so they are not reverted. If unfinished changes need keeping, use the `wip:` checkpoint of `/e`.

**no-progress stop** — repairing verification failures is not endless: **after the first failure the hypothesis·strategy must change, and if there is still no observable improvement after changing it, stop at the second** and go to the verdict above. Only *code fix failures* are counted — transient failures such as network·infrastructure are not. Record which acceptance item·which failure·what was tried and what did not change in `# Blockers` (for NEEDS-HUMAN, in its `NEEDS-HUMAN:` Task).
- **No counter reset**: do not turn the count back by reclassifying a failure under another name, weakening a test, or changing the acceptance wording·pass criterion·verification command. If those three really must change, **user approval + recording old value → new value in `# Decisions`** comes first (an extension of CLAUDE.md §7's ban on weakening tests).
- Identify acceptance items by the plan's item numbers so that the count carries over across sessions.
- Hooks do not count on your behalf — the current ledger (`dlc-evidence-ledger`) does not consume tool responses and has no stable failure signature·acceptance mapping. Mechanizing it would be a separate task, starting from that.

**Notification** — a terminal transition is **a necessary condition for `PushNotification`, not a sufficient one**. Only when the user's attention is actually needed, **at most once** per transition. For BLOCKED/NEEDS-HUMAN, state in one line what must be asked. For DONE, **only when it took long enough that the user has likely stepped away** — for short work the Report is already in front of them, so it would be a duplicate. If the tool skips because it reports being attached, that is normal; do not retry. trivial work·immediate answers are exempt.

## Commit units (medium or larger · 2+ purposes)
Medium or larger work with two or more purposes **makes intermediate commits per purpose**; follow-up fixes to a committed unit are stacked as `fixup!` and `commit-check` folds them at the end — committing a purpose before it mixes with another within one file removes the need for after-the-fact hunk splitting (commit-check does not support it). small·trivial keep the single commit of step 16.
- **Declaration** (step 3 draft plan): in `# Decisions`, `커밋 단위: 1) <unique commit title> — <paths/scope> 2) …`. With one purpose, `커밋 단위: 1개 — <reason>`. Titles must not overlap between units, and none may be a prefix of another — `fixup! <title>` matching and rediscovering shas after compaction (`git log --format='%h %s' $(git merge-base HEAD <default branch>)..HEAD`) rely on the titles. If purposes increase during implementation: if the mixed changes separate by path, first commit the earlier purpose as a unit; if they mixed within the same file, keep them as one unit and write the reason in `# Decisions`.
- **Unit commit** (after step 10): when one unit's implementation and that unit's targeted verification (Green) pass, stage only that unit's paths and commit with the declared title. **Do not include the plan·log files** (they are updated at every step, so putting them in an earlier unit causes a 3-way conflict with later units — only in the last commit of step 16). A file that two units both change goes into the earlier unit **up to the changes the earlier unit needs to work** (leave them out and checking out only that commit breaks). If two purposes are already mixed within one file and cannot be separated by path, merge the two units into one.
- **Follow-up fixes** (steps 11~15 review fixes·simplify·verification repairs): when fixing a committed unit, commit only that unit's paths with `git commit --fixup=<unit sha>` — again, only after targeted verification passes. If it spans two units, split it into per-unit fixups. But if a fix aimed at an earlier unit touches **a file the later unit also changed**, folding it into the earlier unit causes a 3-way conflict, so send that fix as a fixup of the later unit and note it in the Report as an attribution exception. A new purpose is added to the declaration and becomes a new unit.
- **Review·simplify range**: with unit commits the default `git diff` is empty, so pass `git diff <work base>...HEAD` + the working-tree changes explicitly as the range to code-reviewer·architecture-reviewer·the simplify check.
- **Wrap-up** (step 16): commit the remaining **code** changes as fixups of their attributed units per the follow-up rule above, and commit the **record files** such as the plan — and only those — as a fixup of the last unit; then `commit-check` proposes folding them via `fixup_of` (applied after approval). If `fixup!` commits remain because of a conflict or because the commit-check proposal was left unapplied, DONE is not reverted, but write "leftover fixup! commits — rerun commit-check or clean them up before push·`/e merge`" under the Report risks (once pushed, they fall outside commit-check's range and can no longer be cleaned up).

## Investigation protocol (debugging·incidents)
For bugs·incidents, before any guessed fix (making CLAUDE.md §1 root cause·3 Whys concrete): **reproduce** (no "fixed" without a reproduction) → **causal chain** (establish symptom→direct cause→root cause with evidence — if the cause is uncertain, include the evidence that refuted the other candidate causes; no fix that only suppresses the symptom). If possible, a reproduction test first (TDD Red) — green is the acceptance evidence. Elaboration of each step in `~/.claude/wiki/docs/dlc-details.md` §B.

## structural full pipeline (state transitions)
```
0  Setup            git status · size judgment · plan file
1  Explore
2  researcher       [conditional · isolated]
3  draft plan       look up related decisions (first — wiki integration below) · test strategy · rollback · impact scope · structural intent · # Acceptance itemization · ⚠️ self-flag (when applicable) · `intent:` link (if in a bundle) · commit unit declaration · every step of the size table in Tasks from the start (a Task added later states its reason; a conditional step that does not apply or a step the user decided to skip is closed as `- [x] <step> (YYYY-MM-DD) — 생략: <reason>`)
4  arch planning    [isolated · structural only · codex off · first prompt line `mode: planning`]
5  plan revision
6  plan-reviewer    [isolated · codex owner]
7  apply findings   dispose of the ⚠️ self-flags first, together with the review findings · if the structure changes, rerun 4~6
8  TDD Red          confirm the new tests fail for the intended reason · put the identifiers of the tests written into the # Acceptance verification fields
9  implementation   report `⚠️ (구현)` (steps 8~15, when applicable — self-flag section)
10 Green            minimal test/build/typecheck → a finished unit gets a unit commit (with 2+ purposes)
11 arch (detailed) + code-reviewer   [isolated · parallel · 1 codex owner · first arch prompt line `mode: post-implementation` · input includes the **paths** of the plan·(if any) plan log · with unit commits, range `<base>...HEAD`+working tree · pass `⚠️ (구현)` to code-reviewer as review first]
12 fix loop         relevant reviewers only · ≤2 rounds · disposition · fixes to committed units as fixups · dispose of `⚠️ (구현)` (new lines go to the re-review)
13 simplify check   [main agent directly · only when there is no blocker]
14 re-review        targeted, on a substantive edit from the simplify check · pass on new `⚠️ (구현)`
15 final verification   lint / typecheck / test / build   [isolated runner · run only]
16 wrap-up          evidence gate (check every # Acceptance item · completion only after it passes) → verdict (DONE/BLOCKED/NEEDS-HUMAN) → plan update → formal completion commit (DONE only) → commit-check → notification (at most once, when needed) → Report
```

## wiki integration (CLAUDE.md §11)
Ingest proposals are conditional·opt-in and do not lengthen the 16-step table. **But the decision lookup before planning is mandatory** — before the draft plan (step 3; for small without a plan, before starting the implementation), look up both wikis with this work's **target asset name and work type** (slim·compress·migrate·restructure·remove·config change, etc.) and read the decisions·lessons that come up — `uv run --no-project python "$HOME/.claude/skills/wiki/wiki_search.py" <asset name> <work type>` (the shared wiki regardless of the cwd, the repo wiki searched upward from the cwd; the first line gives the wikis found and their page counts. Usage such as handling exit 2 is in `skills/wiki/SKILL.md` query step 1). Do it even if the plan continues from analysis·investigation in the same session and skipped the step 1 lookup. If a decision comes up, write in the first line of the plan's `# Decisions` whether you follow or overturn it, and if you overturn it, attach the evidence and the user's approval ([[lesson-verify-scaffold-purpose-before-removal]] case 4). The wiki has two layers (the current repo's `wiki/`, the shared `~/.claude/wiki/` — placement rules in §11), so look up the shared one even if the current repo has no wiki. When reading an index directly too, read the shared one by the absolute path `~/.claude/wiki/index.md` — a `~/.claude` worktree has no `wiki/`, so a search by relative path silently passes as "none". **Do not omit the two judgments of the 16 Report**: 1) if it is reusable knowledge (a non-obvious decision·lesson·confirmed external fact), judge **down to the target layer** and propose `/wiki ingest` (not automatic; excluding trivial·one-off work) — if it is a shared-wiki target in another repo, leave the proposal `in a ~/.claude main session: /wiki ingest <summary · public evidence · source (public/private)>` in the Report and the plan log's `# Deferred` (§11 Public check). In a `~/.claude` worktree session too, do not write to the shared wiki; leave the same proposal in the plan log's `# Deferred` and record it from a main session 2) if there were **user corrections·review findings** during the work, judge whether to save §12 feedback memory (if it is a target, **both** the memory file + the `MEMORY.md` index; if not, one line of reason). The mechanics of the Explore wiki read·one-way promotion plan→wiki are in `~/.claude/wiki/docs/dlc-details.md` §C.

## Isolation boundary (hub-and-spoke)
- **Main agent (hub)**: Setup, Explore (thin — delegate only broad searches to the Explore agent), draft plan, TDD Red, implementation, Green (a minimal smoke right after implementation), integration, identifying verification commands·judging results·fixing failures, Report, final judgment.
- **Isolated subagents (spoke, read-only)**: researcher, architecture-reviewer (planning/detailed), plan-reviewer, code-reviewer.
- **Final verification runner (isolated·no Edit·creates verification artifacts)**: the built-in general-purpose — the source stays unchanged; build/test artifacts·caches are created. It receives the verification commands the main agent identified **as exact strings + the worktree's absolute cwd** and runs only the given commands, with no interpretation·edits·re-exploration·repairs (identifying the commands is the main agent's responsibility — 'Verification command not identified' below). ⚠️ **Risk of a silent false-pass if the cwd is missing**. Details of the return contract (structured format·rerun when insufficient) in `~/.claude/wiki/docs/dlc-details.md` §E.
- **Pass the `# Acceptance` text to the runner too** (when there is one) — the runner returns it **mapped** only as `item → observed / not observed / mismatched`. Commands·cwd stay the exact strings received, and the ban on re-exploration·self-repair stays (giving it room to interpret breaks the 'run only' contract). If the main agent's evidence gate verdict disagrees with the runner's report, **stop and record the reason** — today the evidence gate is only self-grading by the context that wrote the code, so this is the only independent check.
- **Verification failures are separate from the step 12 fix loop** — they are objective, so they are not disposition targets (false-positive/wontfix); the main agent fixes and re-verifies until they pass.
- **Verification by the main agent directly (not isolated)**: step 10 Green·step 14 targeted re-verification·trivial verification — short, immediate loops, so isolation overhead is a loss.
- **simplify check (step 13)**: not isolated but **the main agent directly** (every spoke is read-only). Within the diff range, check duplication·excess abstraction·unneeded options/dead branches·dead code·excess defensiveness·replacement by standard utilities·deep nesting (item list in `~/.claude/wiki/docs/dlc-details.md` §E). Preserve behavior · stay in scope · hold back when unsure (proposal only, in the Report). On a substantive edit, targeted test + step 14 targeted re-review are mandatory.
- Subagents do not share context with each other. The main agent passes the inputs as a bundle, and the results come back as each agent's "Summary for the plan".

## fix loop / disposition
- At most 2 rounds. Record each finding in the plan log's `# Review Disposition` as `fix / defer / false-positive / wontfix` (only the main agent writes).
- For a code-reviewer `[plan 대비]` finding, the disposition line carries that tag and the side that changed (`코드`/`plan`/`둘 다`/`없음`) — whether a `fix` aligned the code to the plan or the plan to the code cannot be told from the disposition value alone, and this is what source (3) of the 16 Report "Where to read" judges by.
- `⚠️ (구현)` lines disposed of at step 12 go into the same table, separately from the findings, with the self-flag disposition values (`resolved`/`accepted-risk`/`deferred`). Newly arisen lines go to the next re-review; if the work ends without a re-review, the main agent disposes of them as `[리뷰 미경유]` (path in the self-flag section).
- If the same class remains after 2 rounds, `status: blocked` or an explicit risk accept. (These 2 rounds cap the **disposition of review findings** — the cap on repairing verification failures is a separate axis, the no-progress stop of the verdict section.)

## Self-diagnosis
When writing the plan (at the single-writer re-read), check whether the current action matches the first unchecked Task·the size table, and whether it hits a serious signal below. On a serious signal, stop and get a decision with `AskUserQuestion` (no edits before approval — CLAUDE.md §1). **trivial is exempt**.
- **Serious (closed list)**: a change of direction/requirement/design · skipping plan/review/verification · editing files outside the scope · violating the single writer·isolation boundary · the same failure reproduced twice with the same strategy · risk of a false "verification complete". **If ambiguous, serious** (fail-safe).
- Minor omissions (order·outputs·verification results unchanged, recoverable — e.g. forgetting to check a finished Task) are fixed right away and reported in one line.
- **Link to what exists**: direction errors are CLAUDE.md §2, repeated failures the fix loop (≤2 rounds→blocked), missing steps the size table·promotion — do not build new logic; refer to these.
- **Cap**: re-diagnosis after trigger→response ≤1 time. If it persists, `status: blocked` + notification.

## Workflow Findings (evidence-based self-improvement)
Record only **confirmed workflow failures** during the work (cases where the work went wrong because of a problem in dlc/the conventions themselves) — not a retrospective of every task (prevents an empty ritual). No automatic fixes.
- **Recording triggers** (confirmed ones only): 1) a serious self-diagnosis fired (leaving scope·a missing step·an isolation violation, etc.) 2) the same type of failure reproduced twice 3) **workflow friction·false positives the user explicitly pointed out** (e.g. a hook false positive). Unlike §12 feedback (an immediate correction of how you work), 3) is repeated friction that calls for fixing *operating assets (dlc/hooks/conventions)*.
- **Record (2 places)**: one line in the plan log's `# Workflow Findings` + accumulate in the **shared** wiki's `decision/workflow-failures.md` (for the same failure, only raise the count — dlc is a global asset, so the shared layer. Write it from a main session — in a `~/.claude` worktree session, leave it in the log and do it after returning; in another repo's session, the shared record becomes a §11 proposal). The record format and how it complements the automatic hook signals (`scripts/dlc-signal.js`→`/improve`) are in `~/.claude/wiki/docs/dlc-details.md` §D.
- **Proposal on repetition**: when the same finding **accumulates 2+ times** in the wiki, propose with `AskUserQuestion` "repeated N times — fix it with `wt` in `~/.claude`?". On approval, **wt → dlc in `~/.claude`** (the operating assets live in `~/.claude`, and the change is a file change, so wt is mandatory); on refusal, only keep the record.
- **Self-modification boundary (§1)**: do not modify operating assets (dlc/CLAUDE.md, etc.) on your own without approval. The harness goes as far as finding·recording·proposing; fixes come after user approval. No fully unattended automation (shared wiki [[self-diagnosis-and-improvement-status]]).

## Required outputs / core rules
- plan (CLAUDE.md §10): check (with date)·add `# Tasks` every turn. **Subagents do not write the plan** — the main agent is the single writer; re-read right before writing and merge external changes.
- **Commit (step 16 · CLAUDE.md §8 is the single source of the conditions and prohibitions; this is the procedure)**: the formal completion commit of step 16 (with purpose commits, the last commit holding the remaining changes — "Commit units" section above) is made **after** the evidence gate passes + the plan update — reversing the order leaves the plan update uncommitted, which blocks the §8 automatic cleanup and creates a duplicate `/e` WIP commit. **If the change includes something that changes model behavior, such as rule·skill·agent wording, show the user the changed wording (diff) before committing and get confirmation** (the means of verification of CLAUDE.md §8 — if it has already been observed working as worded in a real session, that replaces it. The same goes for unit commits·fixups. A direction approval is not a wording confirmation — but if the CLAUDE.md §8 handover exception applies, follow its conditions and list the commits in the final report instead of the confirmation). **Path confirmation**: compare `git status --porcelain` with the paths in the plan's `# Tasks` to list the paths this work touched (the fallback when compaction has blurred the edit history — no regressing to `add -A` by guessing). **Message**: that repo's `git log` convention (if none, Conventional Commits `<type>(<scope>): <summary>`) + the `Co-Authored-By` trailer, with the *why* in the body (CLAUDE.md §6 — history goes in the commit, not in comments). **Write commit shas in the Report, not the plan** (writing them in the plan makes the tree dirty again and voids the ordering rule). If it restructured, the shas in the Report are the values after restructuring, and the backup ref·revert command also go in the Report (not in the plan).
