# e — plan end

Record the in-progress §10 plan **against the actual git/code state**, **keep uncommitted changes as a temporary commit**, then wrap up the work. The goal is that the next session can take over right away with `/c`. The automated version of CLAUDE.md §10 **Turn end**·**Completion** + the §8 git rules — **CLAUDE.md wins on conflict**. The counterpart of c (continue).

## When to use
- An explicit `/e` call, or a request like "record progress and wrap up / that's it for today / save it and stop".
- Not for simple questions, exploration, read-only work or one-turn commands. **If there is no plan, do not create one** (that is the job of dlc / the start of work).

## Modes
- **Checkpoint mode** (default, `/e` with no argument or no merge token): steps 1–8 below. No push.
- **Merge mode** (`/e merge` or `/e 머지` — only these two tokens. The words `push` and `PR` are not triggers): steps 1–4 → **M1~M6** ("merge mode" below) → steps 5–8. The user's `/e merge` argument is itself the push·PR·merge instruction (it satisfies CLAUDE.md §8 "push only on request"). If `permissions.ask` fires on `git push`, that is a gate too — if it is refused, stop and do not touch the plan.

## Behavior (8 steps: find → collect state·temporary commit → plan sync → wrap-up report → Jira work summary approval·record → worklog record → worktree cleanup → return to main — a non-main worktree session returns before the worklog)

### 1. Find the plan (same as c step 1)
- `ROOT = git rev-parse --show-toplevel`, `BR = git rev-parse --abbrev-ref HEAD`.
- Search locations (only those that exist, deduplicated): `<ROOT>/plans/`, and if the cwd is a worktree, the main worktree's `plans/` (the first `worktree <path>` of `git worktree list --porcelain`). plans/ is independent per worktree (branch), so look at both to miss nothing (it is tracked, but its content differs per branch).
- **Matching** (§10): the dir whose **dir name** (`<YYYY-MM-DD>-<slug>`) contains `BR` → the one `*-plan.md` in it. 1 → adopt it / 2+ → present the candidates and let the user choose / 0 → fallback.
- **Active plan first** (§10): if a plan was already in progress in the session, it is the target regardless of branch matching (it is not dropped even when branch≠slug).
- **Fallback (0 matches)**: present the `status: in_progress|blocked` plans sorted by `updated` descending → the user chooses. Do not pick one automatically by guessing. If all are done or none exist, "no plan to wrap up" — still run step 2 (temporary commit) and only report.

### 2. Collect work state + temporary commit
- **Collect (`collect-state.sh` once)**: `bash skills/e/collect-state.sh` returns read-only state signals as plain `key: value` (10+ separate git calls bundled into one). This relative path resolves only when the cwd is the root of `~/.claude` (or its worktree) — in other repos call `~/.claude/skills/e/collect-state.sh` by absolute path, and in an isolated worktree session the form `bash "$HOME/…"` can be refused (measured 2026-09-30), so use the absolute path with `$HOME` expanded. **If the helper fails or a field is missing**, say so in the report and fall back to separate git commands. **The field catalog, parsing rules (split on the first `: `, list fields) and per-condition fallback commands are in `~/.claude/wiki/docs/worktree-lifecycle.md` §A** (Read it in the state-collection branch).
- **Temporary commit** ("Temporary commit rules" below): if there are uncommitted changes, keep them as a WIP commit on the work branch. If there are none, skip + state "no changes". **Merge mode makes no WIP** — if there are uncommitted changes, `AskUserQuestion` (commit with a proper message / cancel). This is not a §1 risk confirmation but a direction agreement on "is the work done" (§1 proviso).

### 3. Record the plan sync (the main agent is the single writer; §10)
Re-read the plan (merge external changes), then update it **only from facts** (§1) (for an old-format plan, the §10 mapping table):
- `# Tasks`: check finished Tasks (`(YYYY-MM-DD)`), add new tasks (urgent ones at the top of the unchecked items), clean up stale ones — the first unchecked Task is the next session's immediate action. A Task that changed files names those paths in backticks. If there is a WIP commit, state "continue from the `wip:` commit at the branch tip — commit-check cleans it up (`/e merge` proposes it before push)" in that unchecked Task → c notices it. Do not write the sha (only in the report) — once commit-check folds or rewrites that commit, it points to a commit that no longer exists.
- `# Decisions`: fill in decisions and scope changes from the session (the §10 way — rewrite that decision with its reason, move the displaced option to the rejected ones).
- `# Blockers`: what is blocked + the condition to unblock it.
- frontmatter: `status` judgment (step 4) · `updated:` today.
- **Plan integrity (plan-lint)**: **after writing** the updates above, run `node scripts/plan-lint.js <this plan>` (if present) — it checks the §10 format (frontmatter, mandatory sections, Tasks checkboxes and dates) and **broken Acceptance references**. **Fix violations on the spot** (an additive edit often breaks a reference). If the command fails (script missing, etc.), skip + state it. Not a hard stop.

### 4. Status judgment + wrap-up report
- **Status judgment**:
  - `done` only when there is a **confirmed completion signal** such as a merge or deploy — but switching to done needs **user confirmation** (wrapping up = end of the session, not necessarily the end of the work).
  - **Bundle intent judgment** (when the plan has `intent:`, **at the very point where done is written** — in checkpoint mode the user-confirmed done of this step 4, in merge mode the M4 done commit): read the frontmatter `status` of the plans listed in that `intent.md`'s `# Plans` (a note `dropped` counts as done; **an unreadable item or `(not started)` is not done** — fail-safe). If all are done and every `# Open questions` item is disposed (`(resolved)`/`(carried over → …)`), set `status: closed` + `updated` — an objective judgment, so without confirmation, and **in the same commit as plan done**. If anything remains, keep it open and list the remaining items in the report. `# Out of scope` is not a condition (§10).
  - Blocked → `blocked` + `# Blockers`.
  - Otherwise → keep `in_progress` (checkpoint).
- **Report**: plan location·title·status / temporary commit sha (or "no changes") / items synced / remaining work (unchecked `# Tasks`·`# Blockers`) / "the next session takes over with `/c`". If the plan belongs to an `intent:` bundle and its `# Plans` has `(not started)` lines, **list those lines (`<slug candidate> (not started) — note`) and add "start it with `/wt <slug candidate> — <note>`"** (passing only the slug makes dlc ask for the requirement again) — `/c` does not create plans, so without this note only the first plan gets merged, the siblings are forgotten and the intent stays open forever.
- **Wrap-up options (CLAUDE.md §3-6)**: **the `/e` call itself is the "wrap up" instruction**, so under the §3-6 exception (a flow where the user already gave the next instruction → skip the options) do not create a new AskUserQuestion for work options. However, the approval for writing to the Jira task body in step 5 below is an external write and must always be obtained separately. The wrap-up actions are handled by the worktree cleanup of step 7 (when the conditions hold) and the "next session `/c`" note of step 8. **In merge mode, skip the done confirmation question** — `/e merge` is that confirmation (no duplicate questions — §3-6).

### Merge mode M1~M6 (only for `/e merge`, after step 4 · before step 5)
gh commands, JSON fields, the PR body template and the scenario table are in `~/.claude/wiki/docs/worktree-lifecycle.md` §E (Read it on entry). Only gates, order and closed lists are here.
- **M1 entry gate (hard stop, closed list)** — if any one applies, refuse merge mode + report the reason (do not silently fall back to checkpoint): (1) the branch is main/master or detached (2) no plan (3) an unchecked item in `# Acceptance` — if the section itself is absent, pass and report one line; only items prefixed `[post-merge]` are excluded (do not exclude by judging meaning) (4) `gh repo view` fails (not authenticated, not GitHub, no permission) (5) an unchecked item in `# Tasks` outside the Task(s) that run `/e merge` (including rerun Tasks `/e` wrote) and `[post-merge]` (not applicable to an old-format plan). `<default>` = the name from `git symbolic-ref --short refs/remotes/origin/HEAD` with `origin/` removed → on failure `gh repo view`'s `defaultBranchRef.name` → if that is also missing, refuse. Do not put a remote-tracking ref such as `origin/main` where a branch name goes.
- **M2 PR lookup + pre-check (no external writes)**: first `git fetch origin <default>` (to avoid misjudging from a stale ref), then `gh pr list --head <branch> --base <default> --state all` — 2+ candidates → stop and report. OPEN → reuse (stop and report if it is a draft). **MERGED or CLOSED → do not reuse** (as a skip path there would be no PR to carry the plan done commit, and step 7 conditions 2·3·5 could not pass). **Shortcut**: if `origin/<default>..HEAD` has 0 commits and the plan is already `done`, revert the plan edits step 3 wrote with `git restore` (the merged plan is the single truth — making the branch ahead of base makes `git branch -d` refuse) and go **to M6's confirmation·fetch** without M3~M5.
- **M3 prerequisite — check for uncleaned commits** (before the push and the "M4 first" branch. Skip it on the M2 shortcut): keep `wip`/`fixup!`-type commits out of the PR — once pushed, they are outside commit-check's range (unpublished) and cannot be fixed.
  1. `git fetch origin "+refs/heads/<branch>:refs/remotes/origin/<branch>"` (explicit refspec — if the clone's fetch refspec maps only main, a fetch given just the branch name does not update the tracking ref). If the error says the branch does not exist on the remote (`couldn't find remote ref`), delete the remaining `refs/remotes/origin/<branch>` with `git update-ref -d` (an old tracking ref left after the remote was removed by PR cleanup makes unpublished commits look `published` — a local ref, so no remote impact), record the deleted sha in the report (restore with `git update-ref refs/remotes/origin/<branch> <sha>`) and move on. Stop on any other fetch failure. If it fetched, `git merge-base --is-ancestor origin/<branch> HEAD` — stop on exit 1 (diverged: an ff push is impossible, and commits only on the remote could be mistaken for rewrite targets) or any other non-zero (error).
  2. `uv run --no-project python "$HOME/.claude/skills/commit-check/commit_units.py" pending origin/<default>` (fixed path — this SKILL is loaded from the main checkout). A command failure is a stop, not 0 results. If `unfolded` is empty, go on to M3.
  3. If there is `status: rewritable`, call `commit-check` with the Skill tool with the argument "`/e merge` — clean up `wip`·`fixup` flag commits only" (fold or reword to a proper title; if folding conflicts, retry with reword — the rules are in that SKILL's `/e merge` section). After applying, rerun `pending` and continue only when `rewritable` is 0. commit-check leaving its plan unapplied, apply failure, leftovers, or a flow that cannot ask (unattended) → stop. If you stop after apply succeeded, keep the restructuring and report `backup_ref`·`rollback`.
  4. Do not fix `published` (reached by the remote), `held` (held by another local branch or tag) or `blocked` (range cannot be restructured, `range_error`) (§8 no force-push) — show the title·status·`refs` (for `held`: "after removing that ref, a rerun classifies it again" — the merge or signed commit that ref was hiding may show up and make it `blocked`), then `AskUserQuestion` (proceed as is / stop); in a flow that cannot ask (unattended), stop. If the repo disallows merge commits (M6 squashes, so these commits do not stay in the default history), report without asking.
  - **Stop rule**: do not newly write done. Leave the uncommitted plan edits of step 3 as they are and add a "clean up the commits, then rerun `/e merge`" Task with the reason at the top of the unchecked `# Tasks` (no commit, no push). If the plan is already done (rerun after UNKNOWN·QUEUED·head mismatch), touch neither the Task nor the status.
- **M3 push + secure the PR**: if a new PR is needed because the previous PR is MERGED/CLOSED, **run M4 (plan done commit) first**, then push and create it (`gh pr create` fails with 0 commits). `git push -u origin HEAD` (permission prompt refused or failure → stop, plan unchanged — on the path that ran M4 first a local done commit remains, so revert it to `in_progress` by the recovery rule and report). If there is no PR, `gh pr create --base <default>` (title = the plan title or the first commit subject, body from a scratch file — §E template). Check the PR's `mergeable`/`mergeStateStatus` **before writing done**: CONFLICTING·DIRTY → stop and report the reason (plan unchanged), UNKNOWN → re-query shortly. BEHIND·BLOCKED are normal before required checks, so do not block here; re-evaluate right before M6.
- **M4 plan done commit**: `status: done` · check every Task that runs `/e merge` (add one if missing) as `(YYYY-MM-DD) — PR #N` (old format: `# Progress` "PR #N" · empty `# Next`) → plan-lint (failure → stop, no commit) → commit and push the plan and (if present) the log. If the plan has `intent:`, run step 4's bundle intent judgment here and put the `intent.md` change in **the same commit**; on the recovery below, also revert a `closed` back to `open` together. This moves §10 **Completion** (done at the time of merge) forward to the PR, and the recovery rule below covers the gap. **Recovery rule (hard stop)**: **only when REJECTED is confirmed** in M5·M6, immediately restore `status: in_progress` + uncheck the Tasks M4 checked + `# Blockers` (for a timeout, instead of a Blocker, a Task at the top of the unchecked items "PR #N waiting for checks, rerun `/e merge`") → commit, push, then stop. If the recovery push is refused, keep only the local commit and report. **Once REJECTED is confirmed, do not leave done**; an unknown result (UNKNOWN), waiting (QUEUED) or head mismatch keeps done and closes with a rerun note (report) (below).
- **M5 checks (closed list by exit code)**: compare `gh pr view`'s `headRefOid` with the local HEAD (if different, rerun only M3's push; if still different, stop, plan unchanged) → `gh pr checks <N> --watch` (tool timeout 10 minutes). exit 0 → re-query with **a separate call** `gh pr checks <N> --json name,bucket`; go to M6 only when every bucket ∈ {pass, skipping}; if any is `fail`/`cancel`, REJECTED (--watch does not reflect cancel in its exit); otherwise, if any is `pending` (a check registered after `--watch` returned), run `--watch` and this re-query once more, and REJECTED (timeout) only if `pending` remains. If that call fails with `unknown flag: --json` (gh before 2.50), run instead `gh pr view <N> --json statusCheckRollup --jq 'def ok: .v == "SUCCESS" or .v == "SKIPPED" or .v == "NEUTRAL"; def wait: .v == "QUEUED" or .v == "IN_PROGRESS" or .v == "WAITING" or .v == "PENDING" or .v == "REQUESTED" or .v == "EXPECTED"; [.statusCheckRollup[] | {k: [.__typename, (.name // .context), (.workflowName // "")], t: .startedAt, v: (if .__typename == "CheckRun" then (if .status == "COMPLETED" then .conclusion else .status end) else .state end)}] | group_by(.k) | map(max_by(.t)) | if length == 0 then "NONE" elif all(ok) then "PASS" elif all(ok or wait) then "PENDING" else "NOTPASS" end'` — it keeps the latest entry per check as `gh pr checks` does (a check run by name and workflow, a status by context), except that it cannot tell apart push and pull_request runs of one workflow (`gh pr view` does not export the event). `PASS` → M6; `PENDING` → run `--watch` and this `--jq` query once more and classify again, REJECTED (timeout) if still `PENDING` (the `STALE`·`STARTUP_FAILURE` conclusions, which gh buckets as `pending`, are deliberately `NOTPASS` here — waiting does not fix them); `NOTPASS`, `NONE` or a failure of this call → REJECTED / exit 8 (pending left) or tool timeout → REJECTED (timeout) / exit 1 with `no checks reported` in stderr (lowercase substring match) → re-query 3 times 15 seconds apart, and only if still none, treat it as no required checks and go to M6 (reason: right after the done push, a check run may not be registered yet, a race that can skip CI) / any other exit 1 → REJECTED.
- **M6 merge + result classification + fetch (hard invariant)**: right before merging, recheck `mergeable`/`mergeStateStatus` (CONFLICTING → REJECTED; BEHIND·BLOCKED still present → REJECTED — if they remain after checks passed, branch protection is not met) → `gh pr merge <N> --merge --match-head-commit <headRefOid at M5>` (refused for head mismatch → stop and report, not recovery). **No `--delete-branch`** (CLAUDE.md §8 — it bypasses the separate approval of remote deletion + local deletion fails in a worktree). If the repo disallows merge commits (the setting read with M1's `gh repo view`), `--squash`. Classify the result into four: **MERGED** (`gh pr view`'s `mergedAt` non-null) → `git fetch origin <default>`, then step 5 / **QUEUED** (the command succeeded but `mergedAt` is null — merge queue) → plan unchanged, report "waiting in the queue, rerun `/e merge` when it completes" and stop (no recovery push — changing the head invalidates the queue) / **REJECTED** (merge command failed, permission prompt refused) → recovery rule / **UNKNOWN** (a confirmation or fetch command failed) → plan unchanged, note to re-query, stop. Every other error is a stop with the plan unchanged. **A confirmed `mergedAt` satisfies step 7 condition 4 directly** (for a squash, do not re-derive it even if the git signals are false) — `collect-state.sh` does not fetch, so without a fetch it can never see a server-side merge. A rerun does not reuse MERGED at M2, so it does not call merge again.
- Do not delete the remote branch here — after the local cleanup in step 7, merge mode **always asks once** with `AskUserQuestion` (§8(b); only if the user ordered it with `--delete-branch` does that approval replace it), unless the remote branch is already gone (step 7 remote bullet). If the local cleanup was skipped, postpone the remote question too (step 7 remote bullet).

### 5. Jira task body work summary (after user approval)

If the `jira-task` skill exists, write **only the changes that belong to the task's goal** as outcome-focused one-line items (1–4), together with a to-do list that breaks down the ticket's goal, and build a preview of the addition to the Jira task description (writing rules in `skills/jira-task/SKILL.md` steps 2–3 — leave out process such as rebasing or test upkeep). If a WIP commit was already made, base it on that commit's diff and the items checked that day in the plan's `# Tasks`. If there is no ticket or nothing to write, skip this step.

- **Preview**: run the `jira-task` skill's CLI with the summary file (`--summary-file`) and, only if you made one, the to-do file (`--todo-file`) as arguments (procedure in `skills/jira-task/SKILL.md` steps 5–6). It only reads Jira; if there are existing items for that day, rewrite the summary merging them with this work and rerun the preview. If the fingerprint is `unknown`, do not apply it and report the reason.
- **Approval**: report the preview's ticket, the existing items for that day and the content after replacement, then ask with `AskUserQuestion` "Apply this work summary to the Jira task body?". **Do not run `--post` before the user approves.** If it is not applied, keep only the preview and move to the next step.
- **Apply**: only when approved, run the last preview arguments once with `--date <preview date> --post --expect-existing <preview fingerprint>` appended. The existing task description is preserved and only that day's items are replaced. On a fingerprint mismatch (another session updated it meanwhile) or a Jira error, do not retry; report "not posted" in one line that does not expose credentials, and continue the wrap-up.
- If neither `~/.agents/skills/jira-task/` nor the repo's `skills/jira-task/` exists, skip this step and report "no jira-task skill".

### 6 pre. Out of the worktree (non-main worktree session)
If the session is inside a non-main worktree, before step 6 capture the values of the "Worktree cleanup rules" (`target_path`·`target_branch`·`main_path`) and try `ExitWorktree(action: keep)`. In a session isolated to a worktree, helper calls of the form `bash "$HOME/..."` inside the worktree (worklog, collect-state) are refused by the native Bash guard (measured 2026-09-30 — the absolute path with `$HOME` expanded and `uv run python "$HOME/..."` passed. This can vary by harness version — shared wiki `worktree-isolation-bash-guard`). Up to step 5, things run inside the worktree as now.
- **If it returned**: run steps 6·7 from the original directory (usually main). For the worklog, give the directory name of `<target_path>` as the argument for both preview and registration — without it, main becomes the target. The step 7 re-collection is `(cd "<target_path>" && bash "$HOME/.claude/skills/e/collect-state.sh")`. Do not call `ExitWorktree` again after this.
- **If it is a no-op** (the harness started directly in the worktree): run steps 6·7 inside the worktree as now. Call the helpers by the absolute path with `$HOME` expanded (step 2 path notation). If worklog or collect-state is still refused or fails, skip the step 7 cleanup (leave the worktree so the worklog can be run again).
- If it stopped midway through steps 6·7, the same session continues the remaining steps with the captured values, and a new session enters with `/wt <name>` and runs them again.

### 6. Record the worklog (current worktree — **before deletion**)
At wrap-up, record the AI work time spent in this worktree in the Jira worklog. Run it **before the step 7 deletion** — once the worktree is deleted, it cannot be selected by name and cannot be registered (only displayed). If `~/.claude/skills/jira-worklog/` does not exist, skip this step + one line "no worklog skill".
- **Run**: on POSIX `bash "$HOME/.claude/skills/jira-worklog/run_worklog.sh"` (dry-run), on Windows PowerShell `& "$HOME/.claude/skills/jira-worklog/run_worklog.ps1"` (dry-run) to check the time per day and the target ticket. The launcher prefers `uv`, falling back to `python3`/`python` (on Windows including `py`). Attribution is by per-line cwd, so **even run after returning to main, the time of that worktree is captured exactly** (give the name as an argument). But it must be before the worktree is deleted.
- **Register**: if a ticket is detected (worktree name prefix) and `~/.jira-kit/.env` has a token, continue with POSIX `bash "$HOME/.claude/skills/jira-worklog/run_worklog.sh" --register`, Windows PowerShell `& "$HOME/.claude/skills/jira-worklog/run_worklog.ps1" --register` (if you left for main in step 6 pre, give the same `<name>` as the preview before the flag — `run_worklog.sh <name> --register`) — an upsert of **that worktree's** item for the day (idempotent, no duplicates even if /e repeats. Other worktrees' items on the same ticket are not touched, and Jira sums the ticket total). **No ticket / no token / no session activity → preview only and move on quietly** (do not disturb the wrap-up flow). The user putting this behavior into /e = standing consent to registration (no separate AskUserQuestion).
- **Non-blocking**: a lookup or network failure gets only a one-line report and the wrap-up continues (a worklog failure does not block /e). However, **it does block the step 7 cleanup** — the time of a deleted worktree can never be registered again. Skip the step 7 automatic cleanup in these cases.
  - The worklog ended with non-zero (for any reason — e.g. registration blocked or Jira error 1, config or git error 2, no runner 127).
  - The helper call was refused even when called again with the step 2 path notation.
  - `--register` ran but printed a "등록 불가" warning (incomplete credentials — exit 0, so the exit code does not catch it).
  - No session activity, no ticket and no token file are normal skips with exit 0, so the cleanup continues. If the worklog skill does not exist, this condition does not apply.
- One-line report: the registration result ("registered `<time>` on ABC-1234" · "no ticket/no token → preview only" · "no session activity"). If you gave the name as an argument, check that the output header `[<name>]` is the target worktree. On failure, give the reason and the next command together — if registration was blocked, after checking, `run_worklog.sh <name> --register --allow-large-change`, then enter with `/wt <name>` and run `/e`. To give up the time, `/wt rm <name>`.

### 7. Worktree cleanup (conditional — if merged, without confirmation)
After the wrap-up, clean up the current worktree **if it has served its purpose and can be deleted safely**. If the step 6 worklog ended in failure (step 6 non-blocking bullet), do not judge the conditions below; skip the cleanup. Otherwise, **when all conditions below hold, delete the worktree + local branch without asking** (CLAUDE.md §8(a) — regardless of who merged it). **Remote branch deletion is not part of this — always AskUserQuestion** (§8(b)), unless the remote branch is already gone (remote bullet below).
- **Automatic cleanup conditions (all 6 must hold = AND)**: WIP commits and plan writes after step 2 change the state, so **run `bash skills/e/collect-state.sh` once more right before deletion** (same path notation as step 2) and judge by those signals (do not reuse the step 2 snapshot — re-collection invariant). If you left for main in step 6 pre, get the target worktree's signals with `(cd "<target_path>" && bash "$HOME/.claude/skills/e/collect-state.sh")`. **If the helper fails, a field is missing or it cannot be parsed, skip the cleanup (conservative)**.
  1. **Non-main worktree** (`root` ≠ `mainWorktree`; if it is main, do not propose)
  2. **`detached`=false + plan `status == done`** (confirmed in step 4)
  3. **Working tree clean** (untracked included; skip if `dirty`=unknown)
  4. **Merged into the default branch** — `mergedToLocalBase`=true (the helper judges with `git branch --merged <localDefault>`) **or** `inBase`/`patchInBase`=true. **A merge into local `main` counts too** (in a workflow that does not push, `inBase`, based on `origin/<default>`, stays false/unknown forever, so looking only at it disables the automatic cleanup). If all three are false/unknown, treat it as unmerged and keep it. A squash merge is not detected = it is kept, which is safe. **Exception: if M6 confirmed `mergedAt` in merge mode, this condition holds** — do not re-derive it even if the git signals are false.
  5. **Unsaved artifacts safe** (`git worktree remove`/`--force` loses gitignored `.env` and uncommitted plans — if this worktree's `plans/` has an uncommitted plan or log updated this time, skip the cleanup; if there are `.env` or secret candidates, list what will be deleted; skip if `ignoredStatus`=unknown)
  6. **No process holding the worktree** — if a server or daemon started in this session for verification is still alive, `git worktree remove` fails at the OS level (Windows: "Invalid argument"·"Access is denied"). **Reclaim what this session started before deleting** (identify the target by path and stop it — do not touch user servers or other worktrees' processes). If it cannot be reclaimed, skip the cleanup + report the reason.
  - **The git commands that judge each condition, fallbacks, details of `inBase`/`patchInBase`/`remoteContainingHead`, and the squash/rebase limits are in `~/.claude/wiki/docs/worktree-lifecycle.md` §B** (Read it in the deletion-judgment branch).
  - If any one is unmet, risky or the helper is unavailable, or the step 6 worklog ended in failure (step 6 non-blocking bullet) → skip the cleanup + one reason line in the report ("unmerged → kept"·"dirty → kept"·"plan inside the worktree → kept"·"worklog failed → kept").
- **Run**: when the conditions hold, clean up **without asking** in the order worktree → local `git branch -d`, and report the deleted branch's tip sha in one line (`git branch <name> <sha>` restores it). `git worktree remove` can partly succeed (registration removed but directory deletion failed), so **check the result**, and if a directory is left, handle condition 6 and finish deleting it. Execution details: "Worktree cleanup rules" (+ `~/.claude/wiki/docs/worktree-lifecycle.md` §C).
- **The remote branch is separate** — in checkpoint mode ask with AskUserQuestion only when you judge it needs deleting, in merge mode always ask once with AskUserQuestion after a successful merge + finished local cleanup (§8(b)). Before asking, check `git ls-remote --exit-code origin refs/heads/<target_branch>`: exit 2 means the branch is not on origin (never pushed, or already deleted — e.g. by GitHub's "Automatically delete head branches") — do not ask, delete the stale `refs/remotes/origin/<target_branch>` with `git update-ref -d` if present, and report "remote branch not on origin" in one line (any other non-zero exit is not exit 2 — ask as usual). Do not bundle it into the automatic cleanup. If the local cleanup was skipped (e.g. worklog failure), postpone the remote question too, and — unless the check above gives exit 2 — leave one line in the report "remote branch kept — confirm at worktree cleanup" (keep the order: remote after local deletion).

### 8. Return the session to the main worktree
After steps 1–7, return the session to the main worktree (the work records stay in the worktree, and the next work happens on main). It is **non-destructive** (worktree and branch kept), so it runs automatically.
- **`ExitWorktree` target**: when the session is still in a **non-main worktree** after step 7 (`--show-toplevel` ≠ main path, compared after normalization). If the session was on main from the start, skip.
- If step 7 **deleted the worktree**, or the session already left in step 6 pre → already back on main → skip (no duplicate `ExitWorktree`). The main update below still runs.
- Otherwise (kept, proposal skipped, conditions unmet) → return to the original directory (usually main) with `ExitWorktree(action: keep)`. Regardless of plan `status` — even for an `in_progress` checkpoint only the session leaves; the worktree and branch remain (next time enter with `/wt <name>` and continue with `/c`).
- **If `ExitWorktree` is a no-op** (the harness started directly in the worktree, without `EnterWorktree`) → returning within the session is impossible. Do not force a move — only report "ending the session makes the harness release the worktree" (do not detour through another worktree).
- **Update main after returning (main-autopull ⓑ)**: **only when the session actually returned to main** — when 1) main worktree 2) current branch ∈ {main, master} 3) clean **all hold** — `git pull --ff-only origin "$(current branch)"` once (no hardcoded `main` — avoids mishandling a master repo). **Skip on no-op (still on the feature), dirty, ff failure or no origin** (prevents the destructive merge of origin/main into a feature). No automatic rebase, stash or force (§8). Details in `~/.claude/wiki/docs/worktree-lifecycle.md` §D.
- One-line report: whether it returned to main (or why it could not).

## Temporary commit rules
At wrap-up, keep uncommitted changes on the work branch so they are not lost. **Runs automatically, but the safeguards below are mandatory.**

- **Branch protection (§8)**: if the current branch is `main`/`master` (or the `origin/HEAD` default), no direct commit. Stop and AskUserQuestion — 1) create a new work branch and commit there / 2) skip the commit and only record the plan / 3) cancel. No automatic branch creation or forced commit.
- **Risky file check (§8)**: if `git status` shows suspicious items such as `.env`·`*.key`·`*.pem`·`id_rsa`·certificates·large files (build artifacts, etc.), hold the commit + ask the user (prevents leaking secrets).
- **Commit**: if safe, `git add -A`, then `git commit`. Message `wip: <one-line summary of the work> (e checkpoint)` + the convention trailer (Co-Authored-By). One line in the body: "continue in the next session — a target for commit-check to fold".
- **No push** — §8, only on user request.
- If there are no uncommitted changes, skip the commit.

## Worktree cleanup rules
Only when step 7 deletes the worktree. **The cwd may be inside the deletion target, so order matters** (if the session left in step 6 pre, it is already outside).
- **Capture values before moving**: fix `target_path`·`target_branch`·`main_path` (the first worktree of `git worktree list --porcelain`) **before moving the session** (recomputing after the move points to the wrong target or main).
- **Out of the worktree**: return to the original directory (usually main) with `ExitWorktree(action: keep)` — it cannot remove itself from inside the target. If the session already left in step 6 pre, do not call it again — do not treat the no-op that such a second call returns as the no-op fallback below. **If `ExitWorktree` is a no-op** (the harness started in the worktree), the fallback is `~/.claude/wiki/docs/worktree-lifecycle.md` §C (go through another linked worktree, or skip remove + report) — **no forced progress**. If the move failed and the cwd is inside the target, **stop + report** (no remove).
- **Remove**: after confirming the cwd is outside the target, `git worktree remove <target_path>`. On failure, the stderr branches (untracked → `--force` after confirmation · submodule → `--force` without confirmation when the §C checks pass · file held · partial success prune) are detailed in `~/.claude/wiki/docs/worktree-lifecycle.md` §C.
- **Safety gate (§8) — never without confirmation**: `--force`, `git branch -D` (unmerged) and remote `git push origin --delete` **only after a separate AskUserQuestion confirmation**. Exception: if remove refuses a worktree that meets all step 7 conditions with `working trees containing submodules cannot be moved or removed`, and both submodule checks of `~/.claude/wiki/docs/worktree-lifecycle.md` §C pass (every module git dir belongs to a submodule that has a working tree; those submodules have no changes, ignored files or commits outside the remote), `--force` is not asked — the only extra things deleted are what the remote-tracking refs have as of the last fetch.
- **Local branch**: `git branch -d <target_branch>` (if `-d` is refused as unmerged, `-D` only after confirmation). **Remote**: only after the worktree and local deletion succeeded, and only if the user chose remote deletion, `git push origin --delete <target_branch>` (no-op if the remote ref does not exist). Merged as seen from git signals (step 7 condition 4) is not definitive, so put its basis in the question (whether it is merged only into the local default, or `inBase`/`patchInBase`) and delete only if the user who saw it chose to (prevents losing an unmerged remote copy). A `mergedAt` confirmed by M6 is definitive. No other push.
- One-line report: the removed worktree and branch (or the reason they were kept).

## Boundaries (what this skill does not do)
- **Checkpoint mode does not push** (§8). push, PR and merge happen **only in merge mode (`/e merge`·`/e 머지`)** — that argument is the instruction. The words `push` and `PR` are not triggers. **No direct commit to main/master** — split it off after confirmation.
- If there is no plan, **do not create one** — only a temporary commit + a "no plan to wrap up" report (if a plan looks worthwhile, one line proposing dlc). In merge mode, no plan is an M1 refusal reason.
- **No automatic switch to done** — only with a confirmed completion signal + user confirmation. The default is an in_progress checkpoint. In merge mode, `/e merge` is the confirmation for the M4 done, and a failed merge reverts it by the recovery rule.
- Plan updates are **facts only** (§1) — only what git or files confirm. Do not check Tasks or fill Decisions by guessing.
- Not delegated to a subagent — the main agent is the plan's single writer. The main agent commits and records directly.
- **Worktree cleanup runs without confirmation when the step 7 conditions (non-main, done, clean, merged, no unsaved artifacts, no holding process) hold** — if any one is unmet, or the step 6 worklog failed, skip the cleanup (do not force it). `--force` (except the submodule exception of the cleanup rules), `git branch -D` (unmerged) and **remote deletion (`git push origin --delete`)** are not part of it and are forbidden without explicit confirmation (§8).
- **Returning to main (step 6 pre, step 8) is automatic** — `ExitWorktree(action: keep)` is non-destructive, keeping the worktree and branch, so it runs without confirmation. But deletion (remove) is a step 7 matter, not step 8, and on a no-op (the harness started in the worktree) only report, without forcing a move.
