# lesson-test-after-implementation

`native-overlap-lint.js`(PR #139) 를 **구현 먼저, 테스트 나중**으로 썼다(CLAUDE.md §7 순서 위반). 테스트를 쓰는 순간 경계 결함 2건이 드러났는데, **둘 다 테스트를 먼저 썼으면 구현 전에 잡혔을 것**이다. 사용자 지적이 아니라 자진 기록(§13).

## 드러난 결함 2건

| 결함 | 증상 | 왜 눈으로 안 보였나 |
|---|---|---|
| 날짜 롤오버 | `checked: 2026-02-30` 이 `Date.parse` 에서 **03-02 로 조용히 롤오버** → 오타 날짜가 통과하고 신선도가 틀어짐 | `/^\d{4}-\d{2}-\d{2}$/` 를 통과하니 "검증했다"고 느꼈다. ISO 파서가 범위를 거부할 거라고 **가정**했다 |
| 로컬/UTC 경계 | `checked: <오늘>` 이 **"미래"로 판정** → 방금 적은 대장이 skip 됨 | 로컬 달력 날짜(사람이 적는 값)를 UTC 자정 instant 와 비교. UTC+9 에서 로컬 오전은 아직 UTC 어제라 **KST 오후에 돌리면 재현이 안 된다** |

## 원인 (3 Whys)

1. **왜 구현 후에야 드러났나?** — 구현 중엔 "정상 입력 하나"로만 돌려봤고, 경계값을 나열한 건 테스트를 쓰는 시점이었다.
2. **왜 경계값을 그때야 나열했나?** — 테스트 작성이 *경계값을 강제로 열거하게 만드는 유일한 단계*인데 그걸 뒤로 미뤘다. 구현 중엔 "이 정도면 되겠지"가 검토를 대신한다.
3. **왜 미뤘나?** — 로직이 "frontmatter 한 줄 파싱"이라 작아 보였다. **분량으로 TDD 필요 여부를 판단**한 것이 근본 원인 — 실제로 위험한 건 분량이 아니라 *경계가 있는 도메인*(날짜·시간대·버전·인코딩)이었다.

## 잘못된 방법 / 올바른 방법

- ❌ 코드가 짧으니 테스트는 나중에 붙인다 → 짧은 코드일수록 날짜·TZ·버전 파싱이 통째로 들어가 경계 밀도가 **높다**.
- ❌ 정규식이 형식을 검증하니 값도 유효하다 → 형식 통과 ≠ 값 유효(`2026-02-30`). 파서가 **정규화(롤오버)하는지 거부하는지**를 확인하고, 정규화한다면 **왕복 대조**(`파싱 → 재포맷 → 원본과 비교`)로 막는다.
- ❌ 내 머신에서 돌려봤으니 된다 → 시간대·로케일 의존 로직은 한 머신에서 **하루 중 특정 시간대에만** 깨진다. 시각·오늘 날짜는 인자로 **주입**하고 TZ 를 바꿔가며 돌린다.
- ✅ **경계가 있는 도메인이면 분량과 무관하게 Red 부터**: 날짜/시간대/버전/인코딩/경로. 테스트 파일에 경계값을 먼저 나열하는 것 자체가 설계 검토다.

## 연결

- [[lesson-parser-precedent-partial-mirror]] 와 같은 계열의 실패다 — 그쪽은 *선례 파서의 전처리를 안 베껴서*, 이쪽은 *경계값을 안 세워서*, 둘 다 **"형식은 맞는데 무음으로 틀린 값"** 을 통과시켰다. 공통 처방: 파서를 새로 쓸 때 경계·전처리를 먼저 목록화.
- [[evidence-gate]] 가 요구하는 "증거로 충족"은 **테스트 통과 시점**에 생긴다 — 순서를 뒤집으면 증거가 구현을 뒤늦게 쫓아온다.
- 이 결함들을 잡아낸 모듈 자체는 [[native-overlap-ledger]] 의 신선도 판정기다.
