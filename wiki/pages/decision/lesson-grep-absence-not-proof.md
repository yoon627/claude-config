# lesson-grep-absence-not-proof

`grep` 무매칭(빈 출력)을 **"대상이 없음"으로 단정**하지 말 것. 무매칭은 "이 패턴이 안 맞았다"일 뿐, 부재의 증거가 아니다. 특히 **문서 동기화 필요 여부 판정**처럼 결론이 "불필요"로 빠질 때 위험하다 — 패턴이 빗나가면 필요한 동기화를 통째로 건너뛴다. 검색 결과가 요약 모델을 거쳤거나 표본만 봤을 때도 같다 — "없다"·"N건"의 범위는 도구가 실제로 본 범위를 넘지 못한다(사례 5·6). 합계·비중도 같다 — 무엇이 1건인지, 어떤 단가·분포를 가정했는지 확인하기 전에는 결론이 아니다(사례 7).

## 사례 (이 lesson 의 발단)
CLAUDE.md 에 §13 을 추가한 뒤 "README 동기화 필요한가?"를 `grep '## 1[0-3]' README.md` 로 점검 → 무매칭 → **"README 는 절 번호 미러링 안 함, 동기화 불필요"로 단정**. 실제로 README Components 의 `### CLAUDE.md` 절은 헤더(`##`)가 아니라 **본문 리스트**(`12. 피드백 메모리 …`)로 14개 절을 나열하고 있었다. 패턴이 그 형식을 못 잡았을 뿐, README 는 갱신 대상이었다. `dlc-early-stop` 의 doc-drift 경고가 포착해 바로잡음([[evidence-gate]] 보조망의 가치).

## 사례 2·3 — 무매칭이 아니라 **범위 누락**과 **결과 오독** (2026-09-04)
같은 실패가 검색이 *매칭됐을 때도* 난다. 한 세션에서 2회 재현:

- **사례 2 (범위 누락)**: dlc 단계 번호를 바꾸기 전 영향 범위를 `grep -rn ... CLAUDE.md README.md docs/ skills/ scripts/` 로 조사하고 **"참조는 3곳"으로 plan 에 확정**. `wiki/` 를 검색 대상에서 빼서 실제 9줄/5파일 중 6줄을 놓쳤다(`wiki/index.md`·`wiki/pages/concept/…`·`wiki/pages/decision/…`). plan-reviewer 가 전수 재조사로 잡았다.
- **사례 3 (결과 오독)**: 후속 작업에서 `grep -rn "trivial"` 결과에 `skills/c/SKILL.md:68` 이 **분명히 나왔는데**, "결론은 여전히 참(부분집합)"이라 판단해 유지 대상으로 분류했다. 실제로는 그 문장이 역함의(`¬비trivial → ¬wt`)를 심어 규약 구멍을 다시 여는 위치였다. code-reviewer 가 잡았다.

즉 실패는 "grep 이 안 잡았다"만이 아니라 **"내가 검색 범위를 좁혔다"**, **"잡힌 걸 내가 무해하다고 판정했다"** 로도 온다. 셋 다 결론은 같다 — *영향 없음/부재를 자기 검색·자기 판단으로 확정*.

## 사례 4 — 내가 부른 grep 이 grep 이 아니었다 (2026-09-25)
ps1 파일을 UTF-8 BOM 으로 바꿔야 하는지 보려고 Bash 도구에서 `for f in …; do n=$(LC_ALL=C grep -c $'[\x80-\xff]' "$f"); …` 를 돌렸고, 모든 파일이 `0` 이라 **"BOM 없는 ps1 은 모두 ASCII"** 로 plan 에 적었다. 바로 전에 다른 식(`'[^ -~\t]'`)이 같은 파일에서 58줄을 셌는데도 두 결과를 대조하지 않았다. plan-reviewer 가 em dash·한글을 찾아 반박했다.

2026-09-26 재현으로 원인을 확정했다: 도구 셸의 `grep` 은 셸 함수라 내장 ugrep 7.8.4 가 돌았고, ugrep 은 이 바이트 범위식에 0 을 낸다. 같은 식을 단순 명령으로 치면 rtk 훅이 `rtk grep` 으로 바꿔 panic 하고, `bash script.sh` 안에서는 시스템 grep 이 정답(2)을 낸다([[claude-code-bash-tool-shims]]). 처음에는 "grep 바이트 범위식이 깨졌다"로 기록하려 했는데, 재현해 보니 식은 멀쩡했다 — 원인 기록도 재현 없이 쓰면 틀린다.

## 사례 5·6 — 요약과 표본으로 부재·빈도를 확정 (2026-09-27)
[[native-overlap-ledger]] 재판정에서 리뷰가 잡은 실수 두 건이다.

- **사례 5 (잘린 요약을 전문으로 읽음)**: researcher 가 WebFetch 로 Claude Code changelog 창(v2.1.223~283)을 대조했다. docs 페이지는 v2.1.275 부근에서 잘렸고 GitHub 버전 비교 diff 도 요약 모델을 거쳐 버전 귀속이 흔들렸는데, 그 결과로 대장에 "UserPromptSubmit 관련 변경이 창에 없다"고 적었다. 전문을 읽었다던 v2.1.265~283 에 v2.1.271(auto mode 의 subagent 보고를 hand-back 턴으로 바꿈 — 바로 이 repo 의 라우터 hook 을 깨뜨린 변경)과 v2.1.280 이 있었다 — 잘린 지점보다 앞이라 잘림이 아니라 요약 과정에서 빠졌다. code-reviewer 가 원문으로 잡았고, 원문을 받아 2,326줄을 끝까지 읽어 다시 확정했다.
- **사례 6 (표본으로 빈도를 셈)**: 라우터 오발동을 눈앞에서 본 1건만으로 "1회 관측"이라 적었다(같은 세션에만도 41건이 있었다). 리뷰 뒤 이 세션 transcript 로 "41건"으로 고쳤는데, 재리뷰가 2026-09-15 부터 14개 세션에 걸친 오발동을 보였고 전체 transcript·telemetry 로 다시 세어 130건이 됐다. 수치(1 → 41 → 130)와 시작 시점(09-27 → 09-24 → 09-15)이 두 번씩 과소·늦게 적혔고 런타임 범위도 틀렸다([[workflow-failures]]).

둘 다 도구가 실제로 본 범위(잘린 문서, 한 세션)를 결론의 범위("창 전체에 없다", "N건")로 썼다.

## 사례 7 — 1건의 단위를 확인하지 않은 합산, 대표하지 않는 표본 (2026-09-28)
토큰 절감 방향을 정하려고 transcript 30일을 집계한 작업에서 두 번 틀렸고, 둘 다 사용자에게 보고한 뒤 방향 재검토 중에 스스로 다시 세다가 발견했다([[claude-code-context-cost]]).

- **사례 7a (중복 합산)**: assistant 레코드의 `usage` 를 그대로 더해 30일 cache read 합계를 보고했다. transcript 는 응답 하나를 content block 마다 한 줄씩 적고 줄마다 같은 `usage` 를 반복한다 — `message.id` 로 중복을 없애면 합계는 약 2.4배 작았다(이 표본). 같은 보고의 "cache read 가 비용의 68%" 는 중복 탓이 아니었다 — 중복 줄은 같은 값이라 비중은 거의 그대로이고, 차이는 단가 가정에서 났다(일반 배수 0.1×·5분 쓰기 1.25× 로 쟀는데 실제 모델은 Opus 5.5 cache read 0.05×·1시간 쓰기 2× — 모델별 단가를 쓰면 47.5%).
- **사례 7b (비대표 표본)**: 빈 디렉토리에서 돌린 headless 세션(기본 컨텍스트 약 5.5만 토큰)으로 "CLAUDE.md 가 36%", "고정분이 탐색보다 크다"고 보고했다. 실사용 호출은 평균 약 46만 토큰이라 CLAUDE.md 몫은 본 세션 호출 평균 대비 약 4.4%(전체 호출 컨텍스트 대비 3.6~6.6%)였고, 결론(슬림화가 우선)이 뒤집혔다.

셋 다 사례 6 과 같은 축이다 — 도구가 본 것(중복된 줄, 일반 단가, 짧은 시험 세션)을 결론의 대상(응답 수, 실제 청구 구조, 실사용)과 같다고 두었다.

- 원인 (3 Whys):
  1. 왜 틀린 수치를 보고했나 — 합산·환산 결과를 점검 없이 결론으로 썼다.
  2. 왜 점검하지 않았나 — 빠른 추정용 스크립트였고, "1줄 = 1 API 호출", "캐시 배수는 0.1×·1.25×", "빈 세션 = 실사용 축소판" 을 확인할 가정이 아니라 사실로 두었다.
  3. 왜 가정이 사실이 됐나 — 레코드 수와 고유 id 수, 가정 단가와 실제 모델 단가, 시험 분포와 실사용 분포를 대조하는 단계가 집계 절차에 없었다. 사용자에게 보고한 뒤 방향 재검토 중 스스로 다시 세다 발견했다([[claude-code-context-cost]] 집계 방법 절에 반영).

## 근본 원인 (3 Whys)
1. **왜 오판?** grep 한 줄 무매칭만 보고 "미러링 안 함" 결론.
2. **왜 무매칭?** 패턴 `## 1[0-3]` 은 마크다운 헤더만 노렸는데 README 의 절 나열은 본문 리스트 형식이라 구조가 달랐다.
3. **왜 검증 부족?** 동기화 필요 판정인데 **대상 파일(README) 구조를 직접 열어보지 않고** 단일 grep 신호로 단정 — 부정 증거를 약한 도구 신호로 확정.

## 올바른 방법
- "X 없음/불필요"를 grep·검색 무매칭으로 단정하지 않는다. 무매칭은 가설을 **반증 못 한 것**이지 입증한 게 아니다.
- 동기화·영향 판정은 대상 파일을 **Read 로 구조를 직접 확인**한 뒤 내린다(grep 은 위치 좁히기 용도, 결론 근거 아님).
- 부재를 주장하려면 **직접 증거**를 쓴다 — 예: gitignore 여부는 grep 대신 `git check-ignore`(이 PR 에서 memory 트래킹 판정에 실제로 적용).
- **영향 범위 조사는 `wiki/`·`docs/`·`plans/` 를 기본 포함**한다(사례 2). 규약·결정·교훈이 사는 곳이라 코드 디렉토리(`skills/`·`scripts/`)만 훑으면 반드시 빠진다.
- 매칭된 줄을 "결론은 여전히 참이니 유지"로 넘기기 전에 **역함의**(`A면 B` ⇒ 독자는 `¬A면 ¬B` 로 읽는다)를 심는지 본다(사례 3). 근거절이 낡으면 결론이 참이어도 다음 독자를 오도한다.
- 범위 판정을 자기 검색으로 닫지 말고 **리뷰어에게 전수 재조사를 명시 과제로 준다** — 사례 2·3 모두 리뷰어가 잡았고, 자기 점검으로는 두 번 다 통과했다.
- 0 을 결론으로 쓰기 전에 검사식을 **알려진 양성 샘플에 같은 실행 경로로** 돌려 1 이상이 나오는지 본다(사례 4). 같은 대상에 두 검사가 다른 답을 내면 어느 쪽도 결론으로 쓰지 않는다.
- 바이트·인코딩 판정은 grep 이 아니라 python 으로 한다 — Bash 도구의 `grep` 은 명령 모양에 따라 ugrep·`rtk grep` 으로 바뀐다(사례 4).
- 외부 문서를 대조해 "없다"고 적기 전에 원문을 받아 로컬에서 끝까지 읽는다. WebFetch 는 큰 문서를 요약 모델로 줄여 뒤쪽이 잘리고 버전 귀속이 흔들린다(사례 5 — 대장 운영 규칙에도 넣었다).
- 빈도·시작 시점은 손에 있는 표본(지금 세션)이 아니라 전체 데이터(모든 transcript·telemetry)로 센다. 표본 수치를 남길 때는 "표본"이라고 적는다(사례 6).
- 로그·transcript 를 합산하기 전에 **1건의 단위**를 확인한다 — 레코드 수와 고유 id(`message.id` 등) 수를 대조하고 중복을 없앤다. 비용 비중은 일반 배수가 아니라 실제 모델의 단가·TTL 로 환산한다(사례 7).
- 시험 환경(빈 headless 세션 등)에서 잰 **비중**은 실사용 분포로 다시 재기 전까지 실사용 결론에 쓰지 않는다 — 사례 6 이 빈도의 표본 문제라면 이것은 분포의 대표성 문제다(사례 7).
- CLAUDE.md §1(추측 금지·코드 보고 답)·§3 Verify(문서 동기화는 evidence gate 항목)의 구체적 실패 양상이다.
